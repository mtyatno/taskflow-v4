### ADR-004: Note Trash via snapshot table `trashed_notes` (bukan kolom `deleted_at`)
- **Date:** 2026-10-02
- **Agent:** Claude
- **Context:** Fitur Sampah note butuh hapus yang bisa dipulihkan 30 hari. ±30 query di `webapp.py` membaca `scratchpad_notes` (list, search, titles, backlinks, halaman publik, export, bot); soft-delete lewat kolom memaksa semua query difilter dan satu yang terlewat membocorkan note terhapus.
- **Decision:** Hapus tetap menghapus dari `scratchpad_notes` (cascade lama tidak berubah), tetapi dalam transaksi yang sama menulis snapshot JSON (semua kolom + tag + pin + publish + lampiran) ke `trashed_notes`. Restore memasukkan kembali dengan id asli. Purge lazy setelah `NOTE_TRASH_RETENTION_DAYS = 30`. Endpoint `/api/scratchpad/trash*` hanya online (router lokal & SW tidak melayaninya). Spec: `docs/superpowers/specs/2026-10-02-note-trash-design.md`.
- **Consequences:** Query lama tidak tersentuh. Klien: setelah restore buang op outbox `delete` tertunda (`noterepo.discardPendingDelete`) dan pull memperbarui `linked_to_cids` basi. Keterbatasan: perangkat lain yang mengedit note saat note dihapus membuat salinan baru (POST setelah PUT 404) → setelah restore ada 2 note. File lampiran Nextcloud tidak dibersihkan saat hapus permanen (perilaku lama). Deploy wajib restart service agar `migrate_db()` membuat tabel.

### ADR-005: Pesan Pribadi (DM) di tabel terpisah, tanpa ikatan ke shared list
- **Date:** 2026-10-03
- **Agent:** Claude
- **Context:** Diskusi hanya mendukung chat grup (`messages.list_id`). Pemilik produk ingin DM 1-on-1; memulai hanya dengan sesama anggota grup (anti-spam), tetapi percakapan tetap aktif walau keduanya tidak lagi satu grup.
- **Decision:** Tabel baru `dm_conversations` (pasangan ternormalisasi `user_a < user_b`, UNIQUE), `dm_messages`, `dm_reads` (penanda baca per user = `last_read_id`). Cek berbagi grup hanya saat membuat percakapan baru; akses berikutnya hanya cek peserta (404 untuk selainnya). Tidak ada FK ke `shared_lists`. Endpoint `/api/dm/*` online-only (SW network-only, tidak ada rute lokal, tidak memakai chatrepo). Notifikasi in-app ditahan bila penerima subscribe SSE percakapan (`dm_subscribers` menyimpan `(user_id, queue)`), dan tidak diduplikasi selama notifikasi identik belum dibaca. Spec: `docs/superpowers/specs/2026-10-03-direct-messages-design.md`.
- **Consequences:** Hapus/keluar grup tidak memengaruhi DM; hapus akun menghapus DM-nya (CASCADE). `dm_subscribers` per proses — dengan beberapa worker uvicorn, SSE & penahanan notifikasi hanya akurat dalam worker yang sama (sama seperti chat grup). Deploy wajib restart service.
- **Addendum 2026-10-04 (Blokir):** tabel `dm_blocks (blocker_id, blocked_id)` per pasangan user (bukan per percakapan). Blokir dari salah satu pihak menolak kirim kedua arah (403 "Obrolan ini diblokir", tanpa notifikasi/SSE) dan menolak percakapan BARU; percakapan lama tetap dikembalikan & riwayat tetap terbaca. Buka blokir hanya menghapus blokir milik sendiri.

### ADR-006: Outbox dengan klasifikasi error, CAS/rev per record, `base_rev`/409 + salinan konflik, `client_id` idempoten
- **Date:** 2026-10-15
- **Agent:** Claude
- **Context:** Audit offline/sync (`docs/superpowers/specs/2026-10-15-offline-sync-audit.md`) menemukan kehilangan data diam-diam: token kedaluwarsa menghapus IndexedDB + outbox; push membuang op pada semua 4xx lalu pull menimpa record dirty; LWW berbasis `updated_at` (jam dinding, 3 format/zona) dikalahkan oleh proses non-pengguna (cron Eisenhower, `/share`, membuka note); record ditulis dari objek pra-request (edit in-flight hilang); POST tanpa idempotensi menggandakan task/habit/mindmap/pesan.
- **Decision:** (1) 401 = sesi berakhir, bukan ganti pengguna: data lokal dipertahankan, push setelah login ulang. (2) Respons push diklasifikasikan: jaringan/401/429/5xx → op tetap; 403 → `conflict:"access_lost"`; 404 → `conflict:"remote_deleted"`; 4xx lain → op dibuang + `record.sync_error` dan ditampilkan di conflict bar (Coba lagi / Buang). Record `dirty` tanpa op diantre ulang oleh pull, tidak ditimpa. (3) Setiap record punya `rev` (naik di tiap tulis lokal); semua tulis setelah jeda async lewat `TFdb.mutate` (satu transaksi baca-ubah-tulis); push menandai bersih hanya bila `rev` tidak berubah (`markPushed`). (4) PUT task/note/mindmap/drawing membawa `base_rev` opsional; server menjawab 409 `{"detail":{"code":"REV_MISMATCH","current":<row>}}` bila beda. Untuk note & mindmap konflik edit-vs-edit (409 atau pull) TIDAK memakai LWW: versi lokal disimpan sebagai entitas pribadi baru "(konflik) <judul>" (client_id baru), record asli mengadopsi server + notice `conflict_copy`; tidak dibuat bila isinya sama. Task tetap LWW (field kecil), drawing memakai three-way merge dengan `base_blob_ref`. (5) Semua create mengirim `client_id` (= cid); server mengembalikan baris yang ada bila `(user_id, client_id)` cocok (index unik parsial). (6) `updated_at` hanya berubah oleh edit pengguna: kuadran cron ditulis tanpa bump; klien mengadopsi field turunan (`quadrant`, `recurrence_end_date`, `recurrence_notif_level`, `completed_at`) terpisah. (7) Pull defensif: cek status HTTP, tiap langkah terisolasi (push selalu jalan), hapus lokal hanya setelah GET per item 404, tulis lewat CAS.
- **Consequences:** Pengguna bisa melihat lebih banyak item di conflict bar (sync_error, access_lost, salinan "(konflik)") — itu disengaja: tidak ada lagi kehilangan diam-diam. Klien lama (modul SW lama) tetap kompatibel: `base_rev`/`client_id` opsional di server. Rev/`client_id` mengubah bentuk record IndexedDB (tanpa migrasi skema; field baru opsional). SW `/` hanya di-cache bila versi index.html = versi SW (S11). Sisa: server masih `datetime.now()` naive (S9) — perubahan ke UTC disarankan sebagai ADR terpisah.

### ADR-007: Sesi login koheren antar-tab + perpanjangan token geser (sliding) dengan batas 30 hari
- **Date:** 2026-10-17
- **Agent:** Claude
- **Context:** Bapak: "sudah login, pindah tab, kadang perlu login lagi". Token disimpan di `localStorage.tf_token` (bersama semua tab) tetapi tiap tab memegang salinan `__token` yang dibaca sekali saat dimuat, tanpa listener `storage`. Akibatnya (direproduksi Playwright): login di satu tab tidak memulihkan tab lain yang sudah di form login (S1); 401 basi di tab lain menghapus token baru dari localStorage (S2); logout di satu tab tidak mengeluarkan tab lain padahal IndexedDB sudah dihapus (S3). Ditambah JWT 72 jam tanpa perpanjangan, dan sejak ADR-006 setiap 401 langsung memunculkan form login (tepat saat tab kembali aktif → `fetchAll` → `sync()`). Server mendahulukan cookie dan mengabaikan header walau token cookie tidak valid/beda akun.
- **Decision:** (1) `localStorage.tf_token` = sumber kebenaran; `__token` disinkronkan lewat event `storage` + baca ulang saat `visibilitychange`/`focus`/`pageshow` (`onSharedTokenChanged`), kecuali tulis localStorage gagal (`__tokenWriteFailed`). (2) Setiap 401 dilaporkan SEKALI dengan token yang dikirim request itu (`api.fetch`, `__syncTransport`, `__syncRawFetch`, `tryAuth`) ke `handleAuthExpired(failedToken)`: localStorage berisi token lain milik akun yang sama → adopsi + ulangi (tanpa form login); token akun lain → diserahkan ke App; selain itu sesi berakhir (hapus token hanya bila masih token yang gagal). Listener `tf:auth-expired` dan laporan 401 di `stepFailed` dihapus. (3) Aksi tab saat token bersama berubah (`sharedTokenAction`): logout manual → reload, sesi berakhir → form login, login akun sama → pulihkan sesi (`__restoreSession`), akun lain → `beginTabReload()` (tab tidak mengirim apa pun sampai reload). (4) Perpanjangan geser: klien memanggil `POST /api/auth/refresh` saat umur token ≥ 1/3 masa berlaku (24 jam dari 72), throttle antar-tab 10 menit, tidak menulis token bila logout dimulai (`beginLogoutGuard`/`tf_logout_at`) atau token berganti saat in-flight. Server: klaim `iat`, `auth_time` (saat login password, dibawa terus), `pwv` (sidik jari hash password); refresh ditolak bila `pwv` beda (password diganti) dan `{renewed:false}` bila `auth_time` > `SESSION_MAX_DAYS` (default 30). Cookie diperbarui hanya bila request membawa cookie. (5) `_resolve_user`: header Bearer → cookie → query; fallback ke kandidat berikutnya hanya bila `sub`-nya sama dengan `sub` kandidat pertama (tanpa verifikasi).
- **Consequences:** Pengguna aktif tidak lagi terlempar ke form login tiap 72 jam; yang tidak membuka app > 72 jam tetap login ulang, dan semua sesi wajib login password lagi paling lambat 30 hari. Semua tab mengikuti satu status sesi (multi-akun paralel dalam satu profil browser memang tidak didukung — IndexedDB dipakai bersama). Trade-off keamanan: token curian bisa diperpanjang sampai 30 hari (dulu 72 jam); logout dan ganti password belum mencabut token yang sudah terbit (ganti password hanya mencegah perpanjangan). Sisa jendela sempit: respons refresh yang dikirim tab lain tepat sebelum logout bisa menyetel ulang cookie httponly (≤ 72 jam). Tindak lanjut yang disarankan: kolom `token_epoch` per user (dinaikkan saat ganti/reset password, dicek di `_validate_token`), URL SSE Tauri dibangun ulang saat token berganti, bootstrap sesi dari cookie untuk magic link Telegram.

### ADR-008: Peta tertaut (Petakan) — catatan satu-satunya sumber data
- **Date:** 2026-10-18
- **Agent:** Claude
- **Status:** Desain disetujui Bapak (brainstorming per bagian); implementasi belum dimulai.
- **Context:** Bapak ingin mindmap dibuat otomatis dari catatan: hierarki node = daftar isi (heading) catatan, dua arah (edit di peta mengubah catatan dan sebaliknya), dengan logika aturan tanpa LLM karena sebagian user tidak ingin datanya dikonsumsi LLM. Dua alternatif ditolak: (a) menyimpan salinan pohon di mindmap + mesin sinkron dua arah — data ganda yang bisa berselisih dan risiko tertinggi merusak isi catatan; (b) mode tampilan di dalam catatan saja — tidak muncul di halaman Mindmap/tab dan menyulitkan pengembangan lanjutan.
- **Decision:** (1) Peta tertaut = baris `mindmaps` dengan `source_note_id` (index unik parsial; sengaja tanpa FK cascade karena Sampah catatan memakai DELETE + restore dengan id yang sama, ADR-004). `data_json` hanya pengaturan tampilan (arah, Justify, lipatan, ringkasan); server menolak `nodeData` untuk peta tertaut. (2) Pohon dibangun ulang dari markdown catatan oleh `static/offline/notemap.js` (fungsi murni, mengikuti aturan heading daftar isi mode edit). Edit peta disusun ulang jadi markdown — bagian lama disalin byte per byte, identitas node lewat `nm.sid`, level heading mengikuti aturan saudara/induk, batas H6 — lalu ditulis lewat `noterepo.applyMapEdit` di dalam `TFdb.mutate` atas isi catatan terbaru; bila isi sudah berubah, edit dibatalkan dan peta dimuat ulang (tidak digabung). (3) Pemilik dan `list_id` peta selalu sama dengan catatan; server menyamakannya setiap catatan dibuat/disimpan/di-share/dipulihkan, dan menghapus peta saat catatan dihapus permanen. (4) Pengaturan tampilan memakai "yang terakhir menang" tanpa salinan konflik; isi peta ikut sinkron dan konflik catatan (ADR-006). (5) `GET` daftar mindmap menyaring peta tertaut kecuali klien mengirim `?linked=1`, supaya APK/cache lama tidak membukanya sebagai peta kosong.
- **Consequences:** Dua arah konsisten karena hanya ada satu sumber data; offline, sinkron, dan konflik tidak butuh mekanisme baru. Peta tertaut tidak bisa memuat isi khusus peta (panah antar node, kurung Summary, link node dimatikan) dan tidak bisa dibuka tanpa akses ke catatannya. Edit peta yang bentrok dengan perubahan catatan harus diulang user. Spec: `docs/superpowers/specs/2026-10-18-petakan-note-mindmap-design.md`.

### ADR-009: Akses publik drawing & lampiran mengikuti "note publish tepercaya"; ekspor DOCX mengikuti akses pengekspor
- **Date:** 2026-10-18
- **Agent:** Claude
- **Context:** Halaman publik (`/pub/...`, tanpa login, satu origin dengan app) dan ekspor DOCX (pendaftaran terbuka) me-resolve drawing/lampiran tanpa filter pemilik: `/pub/drawings/{id}` melayani drawing siapa pun, render publik mencocokkan id/judul lintas user + fallback `id = note_id`, seksi kanvas legacy menanam drawing `id = note_id`, lampiran/backlink/wikilink mengabaikan password note, resolver ekspor lintas user. Isi note bersama bisa diedit anggota, dan note bersama bisa menjadi "pribadi" lewat unshare atau penghapusan workspace (`ON DELETE SET NULL`) tanpa campur tangan pemilik.
- **Decision:** (1) Note publish **tepercaya** = `list_id` kosong + `scratchpad_notes.user_id = published_notes.user_id` + (`last_edited_by` kosong atau = pemilik). (2) Drawing tampil publik hanya bila dirujuk `::draw[id|client_id]` di note tepercaya dan dimiliki penerbit; resolusi hanya lewat id/`client_id` (tanpa judul, tanpa `id = note_id`); seksi kanvas legacy dihapus. (3) Note berpassword: drawing dan lampiran butuh cookie `pub_unlock_{slug}`; "Related" tidak memuat note berpassword; wikilink ke note berpassword hanya dari note tepercaya milik pemiliknya. (4) Metadata user lain di halaman publik di-escape. (5) Ekspor DOCX: drawing hanya milik pengekspor (tanpa tebak judul untuk token id/UUID); lampiran hanya dari note yang bisa diakses pengekspor atau dipublish tanpa password. (6) Semua penolakan = 404 yang sama dengan "tidak ditemukan"; id di luar INTEGER 64-bit → 404.
- **Consequences:** Drawing di note publish bersama dan di note yang terakhir disunting orang lain tidak tampil publik (PR 2 menambah drawing workspace `list_id = W` untuk note bersama). Sisa risiko yang diterima: setelah pemilik menyimpan note lagi, sisipan lama ikut dipercaya (pemilik melihatnya di app). Belum ditangani: XSS isi note (PR 1b), SSRF ekspor, lampiran note bersama di app hanya untuk pengunggah.

### ADR-010: Project sebagai entitas ber-scope (pribadi / satu workspace); teks `tasks.project` tetap disimpan
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Project dulu hanya teks bebas di `tasks.project`; dropdown = `DISTINCT` dari task aktif milik user, jadi project hilang saat semua task selesai, tidak bisa dikelola, dan anggota workspace tidak berbagi daftar project. Bapak memilih project sebagai entitas dengan hak kelola opsi C (spec `docs/superpowers/specs/2026-10-18-workspace-drawing-project-design.md` §5).
- **Decision:** (1) Tabel `projects` dengan tepat satu pemilik (`user_id` XOR `list_id`), nama unik NOCASE per scope, `archived`, `created_by`; `tasks.project_id` FK `ON DELETE SET NULL`. (2) Teks `tasks.project` tetap diisi nama kanonis (bot, NLP, review, filter, klien lama). (3) Satu resolver `resolve_task_project` untuk semua jalur tulis; scope = workspace bila `list_id` menunjuk list yang ada, selain itu pribadi pemilik task; workspace mensyaratkan aktor anggota/owner; resolusi hanya saat project benar-benar berubah. (4) Backfill idempoten di setiap `migrate_db()`, tahan data rusak (SAVEPOINT per grup), memperbaiki link basi, tidak mem-bump `updated_at`. (5) Hak kelola opsi C: pakai/buat = semua anggota; rename/arsip/hapus = pembuat atau owner workspace; 404 bila tak terlihat, 403 bila terlihat tapi tak boleh kelola. (6) `GET /api/projects` tanpa parameter tetap `string[]` pribadi untuk klien lama.
- **Consequences:** Project tidak lagi hilang saat task selesai; dropdown per scope menunggu PR 5. Batasan v1: PUT task LWW tanpa `base_rev` → perangkat offline basi bisa membuat ulang project bernama lama setelah rename/hapus (PR 5 mengirim `project_id` + `base_rev`). Bot `/projects` hanya project pribadi dan kini juga menampilkan project tanpa task aktif.

### ADR-011: Daftar project di klien = cache server per scope + `project_ref_name` pada task
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** SPA local-first melayani `GET /api/projects` dari router lokal (turunan teks task), sehingga tabel `projects` (ADR-010) tidak terlihat dan project workspace tidak bisa dibagi. Perangkat offline yang basi bisa membuat ulang project bernama lama setelah rename/hapus.
- **Decision:** (1) Modul `static/offline/projectcache.js` menyimpan `GET /api/projects?format=full&scope=all&include_archived=1` di `_meta` "projects:v1", di-refresh tiap sync pull; route lokal `GET /api/projects` sadar scope (`?list_id=`, `format=full`), tanpa query tetap `string[]` pribadi. (2) Task menyimpan `project_ref_name`; push mengirim `project_id` selama teks = nama itu (server: id sama → tetap, id terhapus → diabaikan). (3) Kelola project hanya online lewat `api.fetch(..., {network:true})` yang menambah `X-TF-Sync: 1` agar melewati cache SW. (4) Form task memilih scope di baris atribut cepat; tampilan mengelompokkan per (scope, nama NOCASE). (5) Event `tf:projects-changed` setelah pull/kelola.
- **Consequences:** Anggota workspace berbagi daftar project yang sama, juga offline (dari cache + task lokal). `base_rev` task tetap tidak dipakai. Sisa yang diterima: pindah project offline ke project yang dihapus sebelum push → task tetap di project lama.

### ADR-012: Drawing berscope workspace (`drawing_scope.py`)
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Spec §4: drawing harus bisa dimiliki satu workspace seperti mindmap, supaya anggota yang membuka note W melihat semua drawing di dalamnya, tanpa share otomatis yang tidak disengaja.
- **Decision:** (1) Modul `drawing_scope.py` (tanpa impor webapp): skema `drawings.list_id`/`last_edited_by` (FK SET NULL), backfill **sekali jalan** (flag `app_meta['drawing_list_backfill_v1']`), access clause, lookup token id → `client_id` milik sendiri dulu, sinkron note → drawing, aturan publik. (2) `GET /api/drawings` tanpa parameter tetap milik sendiri; `?shared=1` untuk klien baru (PR 3). (3) Share/unshare/pindah hanya pemilik; ditolak 409 `DRAWING_IN_USE` bila masih dipakai note W (judul hanya yang terlihat pemilik + `hidden_count`). (4) **Server memindah drawing hanya saat penulisan menetapkan/mengubah `list_id` note** (share, note baru di W); autosave/PUT biasa dan restore tidak pernah memindah. Sisip drawing pribadi ke note W yang ada → klien memanggil share eksplisit (PR 3). (5) Regex direktif tidak peka huruf besar/kecil, sama dengan klien. (6) Halaman publik: note tepercaya → drawing yang bisa diakses penerbit; note bersama W → hanya `list_id = W`; query `/pub/drawings` dibatasi penerbit di SQL. (7) Hapus workspace mem-bump `updated_at` drawing yang kembali pribadi (`repository.delete_shared_list`).
- **Consequences:** Sampai PR 3, drawing yang disisipkan ke note W yang sudah ada tetap pribadi (anggota melihat placeholder). Sisa risiko yang sama kelasnya dengan §3: note bersama yang di-unshare/workspace-nya dihapus setelah pemilik menyimpannya menjadi tepercaya, sehingga sisipan anggota (drawing pribadi pemilik) bisa tampil di halaman publik. Deploy: restart `taskflow-web` dan `taskflow`.

### ADR-013: Drawing workspace di aplikasi (PR 3) — share online, salin lokal, scope dari server
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Lanjutan ADR-012: klien harus menampilkan, membagikan, dan menyalin drawing berscope workspace tanpa kehilangan edit offline.
- **Decision:** (1) Record drawing lokal menyimpan `list_id`/`user_id`/`last_edited_by`/`last_editor_*`; pull memakai `/api/drawings?shared=1` dan mengadopsi metadata scope setiap kali berbeda (terpisah dari konten). (2) Drawing orang lain yang hilang dari daftar: bersih → dihapus lokal, dirty → konflik `access_lost` (keep_as_new menjadikan salinan milik user saat ini). (3) Share/unshare hanya online lewat `TF.drawingshare.shareDrawing`; **hanya `list_id` yang diadopsi, `base_rev` tidak dimajukan** (PUT drawing tidak membawa `base_rev`, jadi memajukannya menyembunyikan edit anggota lain dari pull). (4) Salin memakai data lokal bila ada (jalan offline), selain itu `POST /copy`. (5) Share note ke W selalu flush + push lalu cek sinkron sebelum `PATCH share`; dialog menyebut drawing yang ikut/disalin, `moved_drawings` di luar rencana di-toast. (6) Hapus/pin drawing orang lain ditolak lokal (403) sebelum masuk outbox. (7) Daftar drawing di halaman workspace (§4.7) diganti filter scope di halaman Draw.
- **Consequences:** SW v421. Setelah update, perangkat mengunduh ulang konten drawing yang di-share satu kali. Sisa diterima: pull yang daftar-nya lebih tua dari share lokal bisa sesaat mengembalikan scope lama (sembuh di pull berikutnya).

### ADR-014: Sampah mindmap = snapshot + cermin offline; pin mindmap per user; `mindmaps.search_text`
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Temuan review mindmap #5–#8 (spec `docs/superpowers/specs/2026-10-19-mindmap-findings-3-8-design.md`): hapus mindmap = hard delete, pin hanya pemilik (anggota gagal diam-diam), `/api/search` mencocokkan `data_json LIKE` (kunci JSON seperti "children" ikut cocok), mindmap tidak ikut ekspor; kartu link node hanya snapshot (#3).

### ADR-015: Kolaborasi langsung mindmap — merge tiga arah per node di klien, SSE hanya sinyal, stream hanya untuk tab aktif
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Temuan review mindmap #4 (spec `docs/superpowers/specs/2026-10-19-mindmap-findings-3-8-design.md` §#4): peta bersama baru berubah lewat sinkron 30 detik, dan edit bersamaan di node mana pun membuat salinan konflik seluruh peta (ADR-006).
- **Decision:** (1) **Merge per node di klien**: `static/offline/mindmapmerge.js` (`TF.mindmapmerge.merge3(B, L, S)`, modul murni) dipakai saat push 409 `REV_MISMATCH`, saat pull menemukan record dirty yang berubah di server, dan di router lokal `PUT /api/mindmaps/:id` (body `base_data_json` dari tab). Basis = `base_data_json`/`base_title` pada record (isi server pada `base_rev`). Node berbeda → digabung tanpa salinan; field yang sama di node yang sama → versi server di peta bersama + salinan pribadi "(konflik) <judul>" versi lokal utuh + notice `merge_conflict`; posisi/urutan/lipatan/panah/ringkasan/pengaturan/judul → server menang tanpa salinan; edit menang atas hapus. Server tetap otoritatif (`base_rev` + 409 tidak berubah) dan tidak tahu basis. Record tanpa basis/JSON rusak/fallback → perilaku lama (salinan seluruh peta). Salinan konflik dari push 409 / pull memicu event window `mindmapConflictCopy` → toast (jalur simpan tab memberi toast dari respons router); merge bersih tidak memberi toast. (2) **SSE hanya sinyal**: `GET /api/mindmaps/{mid}/stream` mengirim `mindmap_changed`/`mindmap_deleted`/`mindmap_access_lost` tanpa isi; klien mengambil isi lewat `pullMindmapOne` di dalam `runSyncExclusive` (bus dalam proses, cukup karena uvicorn satu proses). SW: stream network-only. Sinkron 30 s tetap jadi cadangan. (3) **Stream hanya untuk tab mindmap yang aktif** (ruling controller): HTTP/2 di produksi tidak bisa dipastikan dari repo (konfigurasi nginx tanpa `http2`) dan HTTP/1.1 hanya memberi 6 koneksi per origin, jadi satu `EventSource` per tab terbuka bisa menghabiskan pool. Mengaktifkan tab membuka stream dan `onopen` menarik satu peta untuk mengejar perubahan yang terlewat; tab latar belakang tidak langsung, tetapi mengejar saat diaktifkan. (4) **Undo dikosongkan setelah pembaruan jarak jauh** (`TF.mindmapops.resetUndo` → `clearHistory()` mind-elixir, juga setelah `refresh` dari Outline) — kalau tidak, Ctrl+Z memulihkan pohon sebelum pembaruan dan simpan berikutnya menghapus perubahan anggota lain. (5) **Salinan konflik dipakai ulang per sesi tab**: salinan dari router lokal diberi `conflict_session` = `session_id` instans tab; konflik berikutnya dari tab yang sama memperbarui salinan itu, sedangkan salinan dari pull/409 (tanpa sesi) dan dari tab lain selalu salinan baru — tidak ada salinan yang menimpa isi milik sesi lain. (6) **Peta tertaut (Petakan, `source_note_id`) tidak pernah di-merge dan tidak berlangganan SSE** (stream 404 untuk peta tertaut); ADR-008 tetap berlaku.
- **Consequences:** Deploy wajib `sudo systemctl restart taskflow-web` (endpoint stream + broadcast di `webapp.py`). SW `taskflow-v423-mindmap-live`, iframe `?v=145`. Record mindmap kira-kira 2× ukuran (`base_data_json`). Tab latar belakang tidak live sampai diaktifkan. Edit Outline yang sedang diketik bisa batal bila nodenya hilang oleh pembaruan jarak jauh (diterima). Setelah 8 kegagalan sambung berturut-turut stream berhenti sampai online/aktivasi tab; sinkron 30 s menutup celah. Riwayat undo kanvas hilang setiap kali pembaruan jarak jauh diterapkan. Record yang isinya sama dengan basis tab (gema simpan sendiri, catch-up tanpa perubahan) tidak memuat ulang kanvas. Riwayat undo Outline juga dikosongkan saat pembaruan jarak jauh diterapkan (`historyEpoch`). Pelanggan stream yang dilepas (antrean penuh) ditutup sehingga klien menyambung ulang.

### ADR-019: Papan Kanban tahap: model murni + tahap pending offline di `_meta`
- **Date:** 2026-10-20
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-19-kanban-context-stages-design.md` (§7–§8), di atas backend ADR-016: papan Kanban Group by Context harus menampilkan tahap (termasuk yang kosong) per scope, kolom "Belum ada tahap" dan "Selesai", drag mouse + sentuh, kelola tahap, dan membuat tahap saat offline. Klien sebelumnya hanya mengenal teks `task.context`, drop mem-`parseInt` id (task cid tidak bisa diseret), dan tidak ada jalur "buka lagi" task done.
- **Decision:** (1) **Model papan murni** `static/offline/kanbanboard.js` (tanpa DOM/IndexedDB): bentuk kolom `{key, kind: none|stage|orphan|done|priority|project, …}`, pencocokan task → tahap **id dulu** (`context_id`), lalu nama NOCASE; tahap diarsip / nama tanpa tahap jadi kolom "orphan" (" (diarsip)" / " (belum tersinkron)", bukan target drop); keputusan drop (`dropAction`) dan urutan kartu (P1→P4, deadline, judul NOCASE, id; "Selesai" = `completed_at` terbaru) diuji sebagai fungsi murni. Id task/tahap selalu string apa adanya (`String(a) === String(b)`), tanpa `parseInt`. (2) **Cache tahap** `contextcache.js` (pola `projectcache`, ADR-011): `_meta` `contexts:v1` disegarkan setelah pull; **tahap yang dibuat offline disimpan di `_meta` kunci `contexts:pending:v1`** (R1) — tanpa store IndexedDB baru, `DB_VERSION` tetap 5 — dengan op outbox `{entity_type:"context", op:"create"}`. Op task (create **dan** update) yang `context_id`-nya masih cid tahap pending **ditahan** sampai op tahap terkirim; sukses → cid dipetakan ke id server di semua task lokal (CAS, dirty + rev), gagal permanen → `context_id` dibuang dan task terkirim dengan nama saja. `context_id` cid tidak pernah dikirim ke server. (3) **Rute**: `GET`/`POST /api/contexts` lokal; `PATCH`/`DELETE /api/contexts/{id}` dan `PUT /api/contexts/order` sengaja tidak lokal (kelola tahap = online saja, modal memakai `GET … {network:true}`). (4) **K1** — task berulang ke "Selesai" (drop atau checkbox) menandai *occurrence hari ini* (Asia/Jakarta) lewat `POST /api/tasks/{id}/occurrences/{hari}/mark`, kartu tetap di tahapnya; offline → toast "Tidak bisa dilakukan saat offline". **K2** — keluar dari "Selesai" membuka lagi task dengan `gtd_status:"next"` + context tujuan. (6) **Drag = Pointer Events** (mouse mulai setelah 6 px; sentuh setelah tekan-tahan ≥ 250 ms tanpa bergeser, listener `touchmove` non-pasif dipasang sejak mount), kolom target lewat `data-kanban-col`; menu "Pindah ke…" per kartu sebagai alternatif tanpa drag. Scope papan halaman non-workspace disimpan per halaman di `localStorage` `tf_kanban_scope:<page>`.
- **Consequences:** Kegagalan permanen create tahap tidak tampil di conflict bar (tahap pending bukan entitas store); pengguna hanya melihat toast saat drop/buat dan tahap hilang setelah sync. Klien lama (SW < v426) yang menerima op `context` akan membuangnya (fallthrough `processOp`), sehingga rilis butuh bump SW **`taskflow-v426-kanban-stages`**. "Selesai" hanya memuat 7 hari terakhir; halaman "done" pada mode Kanban tidak lagi menampilkan task done yang lebih lama. Status sebelum done tidak disimpan, jadi K2 selalu memakai `next`. Rename/hapus tahap menarik ulang task (teks context ikut berubah di server, ADR-016). Deploy: hanya file statis + `webapp.py` (`sw_cache`) → restart `taskflow-web` agar `/api/version` melaporkan v426. Diverifikasi E2E Playwright `temporary_files/e2e_kanban_stages.py` (mouse, sentuh CDP, offline, dua perangkat).
- **Biaya R3:** urutan tahap di modal "Kelola tahap" lewat tombol ↑/↓ (satu langkah + satu `PUT /api/contexts/order` per klik) kurang mulus dibanding drag urutan yang disebut spec §7.5; drag tetap ada di papan (kartu antar kolom), dan urutan kolom di papan juga bisa lewat menu ⋯ "Geser ke kiri/kanan".

### ADR-022: pwv diperiksa di setiap request + `users.password_set` untuk akun Telegram
- **Date:** 2026-10-21
- **Agent:** Claude
- **Context:** Klaim JWT `pwv` (sidik jari `password_hash`) sebelumnya hanya dicek di `POST /api/auth/refresh`, sehingga ganti/reset password tidak mengeluarkan perangkat lain sampai token kedaluwarsa (≤ `JWT_EXPIRE_HOURS`). Frontend sudah memanggil `PATCH /api/auth/profile/password` dan `/username` (404). Akun yang dibuat otomatis dari Telegram (`tg_<telegram_id>`) memiliki password acak yang tidak diketahui pemiliknya, sehingga tidak bisa ganti password (butuh password lama) atau login web.
- **Decision:** (1) `_validate_token` memuat `username, password_hash` user (satu lookup PK untuk setiap token). Token non-ext dengan `pwv`: beda/user hilang → 401 "Password sudah diganti — masuk lagi". Token tanpa `pwv` tetap diterima (kompatibel token lama). Untuk semua token (termasuk ext) klaim `username` ditimpa nilai DB bila baris ada, sehingga log aktivitas/notifikasi/mention/pembuatan token ext tidak memakai nama basi. Fallback kandidat di `_resolve_user` tidak berubah. Stream SSE (`chat_stream`, `dm_stream`, `mindmap_stream`) memanggil `_session_still_valid(user)` di setiap keepalive (±20 dtk) dan menutup stream bila password sudah diganti. (2) Kolom `users.password_set INTEGER NOT NULL DEFAULT 1` lewat migrasi idempoten di `_init_db`; hanya saat kolom baru ditambahkan, akun `username = 'tg_' || telegram_id`, atau `telegram_id IS NULL AND username GLOB 'tg_[0-9]*'` (Telegram sudah dilepas), ditandai 0. Register menolak username berawalan `tg_` (case-insensitive); aturan charset baru tidak diterapkan ke register. `auto_register_telegram_user` menyisipkan 0. (3) `PATCH /api/auth/profile/password` (butuh password lama), `PATCH /api/auth/profile/username` (butuh password; `^[A-Za-z0-9_]{3,50}$`, tidak boleh diawali `tg_`, display_name tidak diubah), `POST /api/auth/complete-account` (hanya `password_set = 0`, tanpa password lama; email wajib, username opsional, atomik). Ketiganya menerbitkan token baru (auth_time pemanggil dipertahankan — bila tidak ada, diperkirakan dari `exp` seperti refresh — pwv baru) dan memperbarui cookie hanya bila request membawa cookie `token`; token ekstensi ditolak (403). (4) Ganti password, lengkapi akun, dan `/api/auth/reset` menghapus semua `ext_tokens` user dan menyetel `password_set = 1`. (5) `GET /api/auth/me` mengembalikan `password_set`.
- **Consequences:** Satu query SQLite tambahan per request terautentikasi (lookup PK, murah) dan satu per keepalive SSE. Ganti/reset password langsung mengeluarkan perangkat lain, stream SSE terbuka (dalam ±20 dtk), dan Browser Clipper (harus dihubungkan ulang). Mengganti username tidak membatalkan token lain (pwv tetap); klaim `username` di token lama basi tetapi server selalu memakai nilai DB. Akun tg_ yang mengganti username tidak lagi dianggap "akun otomatis" oleh `/link` di bot (deteksi `startswith("tg_")`). Deploy: restart `taskflow-web` dan `taskflow` (migrasi kolom).

### ADR-024: Komentar note = tabel terpisah `note_comments` (soft delete, `list_id` saat dibuat menentukan visibilitas, tanpa FK ke note)
- **Date:** 2026-10-21
- **Agent:** Claude
- **Context:** Anggota workspace perlu meninjau note bersama lewat komentar tanpa mengubah isi note, dan Alurik local-first (komentar harus bisa disinkronkan offline lewat delta pull berkursor). Note bisa ke Sampah, di-restore, di-unshare, dipindah ke workspace lain, atau workspace-nya dihapus; komentar harus mengikuti siklus itu tanpa bocor ke orang yang tak berhak. Menyimpan komentar di dalam konten note akan mengubah `updated_at` note dan bentrok dengan sinkron note.
- **Decision:** (1) Tabel `note_comments` (id, `note_id` tanpa FK, `list_id` workspace saat komentar dibuat, `user_id`, `parent_id` satu tingkat, `body` 1-4000, `quote` <= 500 hanya di thread, `resolved_at/by`, `edited_at`, `deleted_at`, `client_id`, `created_at`, `updated_at` sebagai kursor) + `note_comment_reads` (`last_read_at` per user per note) + kolom `notifications.note_id`; migrasi idempoten. (2) Visibilitas satu helper `note_comments.visible_clause(uid)` (plus `note_comments.visible_note`): note ada, `n.list_id IS NOT NULL`, `n.list_id = c.list_id`, dan lolos `_note_access_clause`. Karena itu note ke Sampah / di-unshare / dipindah workspace otomatis menyembunyikan komentar tanpa menyentuh barisnya; restore atau share ulang ke workspace sama memunculkannya lagi. (3) Hapus = soft delete (tombstone, `body` dikosongkan; thread menghapus balasannya) agar delta pull `GET /api/note-comments?since=<updated_at>|<id>` bisa menyampaikan penghapusan. Tombstone > 30 hari dibersihkan di `migrate_db()` saat start/deploy; kursor lebih tua dari 30 hari dijawab `{"reset": true}`. (4) Hak: edit hanya penulis; selesaikan/buka lagi thread oleh penulis thread + pemilik note; hapus oleh penulis + pemilik note. (5) Idempotensi POST lewat unique index `(user_id, client_id)`. (6) Badge turunan `comment_open_count` / `comment_unread` di daftar/detail note lewat subquery, tanpa mengubah `updated_at` note. (7) Notifikasi in-app + Telegram lewat `_notify_users_bg`; SSE `GET /api/scratchpad/{id}/comments/stream` hanya mengirim sinyal `comments_changed` dengan cek akses ulang per pelanggan.
- **Consequences:** Komentar tidak ikut Sampah (tidak ada di snapshot), ekspor DOCX/MD, `/pub`, pencarian, dan backlink. Purge note / kosongkan Sampah / hapus workspace menghapus baris komentar permanen. Tombstone bisa bertahan lebih dari 30 hari sampai restart/deploy berikutnya; klien tetap benar karena kursor > 30 hari dijawab `reset` dan klien menarik ulang. Komentar pada note yang dipindah ke workspace lain tetap tersembunyi (bukan dihapus). Tanpa FK ke note berarti pembersihan harus eksplisit di setiap jalur hapus note. PR 2 (offline) dan PR 3 (UI) memakai kontrak ini.

### ADR-027: Cakupan dan bucket waktu halaman Fokus dihitung di klien dengan tanggal lokal

- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-22-fokus-filter-task-design.md`. `is_overdue` dihitung server dengan `date.today()` saat task dikirim, lalu disimpan apa adanya di IndexedDB, jadi basi saat offline atau setelah tengah malam dan bisa berbeda dari tanggal pengguna (WIB, UTC+7). ### ADR-029: Precache SW — shell atomik dan revalidasi
- **Date:** 2026-10-23
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-22-sw-precache-shell-design.md`. Setelah HP restart, Alurik tampil tanpa styling. `/static/app.css?v=362` tidak di-precache dan `milkdown.bundle.js` tercatat tanpa `?v=289`, padahal catch-all `fetch` mencocokkan URL persis dan `activate` menghapus cache versi lain, jadi tiap rilis keduanya wajib diambil ulang dari jaringan (gagal → 503, stylesheet dibuang). Setiap rilis juga mengunduh ulang seluruh precache (`cache: "reload"`).
- **Decision:** (1) `STATIC` = shell: `/`, `/config.js`, setiap `<script src>` / `<link rel="stylesheet">` lokal di `index.html` dengan URL persis (termasuk `app.css?v=362`, `milkdown.bundle.js?v=289`), dan modul `static/offline/*`. `OPTIONAL_STATIC` baru: manifest, ikon (termasuk favicon `icon-32`), font KaTeX, build tldraw + `TLDRAW_ASSETS`. (4) Tes `tests/offline/sw_precache_shell.test.js` menjaga: aset lokal `index.html` ada di `STATIC` dengan URL persis, entri `STATIC` adalah file yang ter-track git, tanpa entri ganda; ikut CI lewat `tests/test_sw_precache_node.py`. `activate`, cabang `fetch`, server, dan skema tidak berubah.
- **Consequences:** Update bisa tertunda sampai jaringan cukup baik untuk memvalidasi seluruh shell. Setiap file baru yang dimuat `index.html` wajib ditambahkan ke `STATIC` dengan URL persis (dijaga tes). tldraw/ikon/KaTeX tetap bisa hilang sampai dipakai online. URL ganda atau URL yang 404 di `STATIC` memblokir semua update (dijaga tes + CI; deploy belum menunggu tes, lihat tindak lanjut H). Perangkat dengan penyimpanan hampir penuh (`QuotaExceededError`) bertahan di versi lama sampai ruang cukup. Setiap percobaan install ulang tetap mengunduh `/` penuh (`no-store`) sampai tindak lanjut F. Perlindungan sudah berlaku untuk rilis v464 sendiri (install/activate yang berjalan milik SW baru). Deploy: file statis + `webapp.py` (`sw_cache` v464) → restart `taskflow-web`; tanpa migrasi.

- **Date:** 2026-10-31
- **Agent:** Claude
- **Context:** Alurik akan mendapat banyak fitur opsional (Timeline/Gantt, Mode Ramadan, Flashcard, dll.) sementara `index.html` (~46 ribu baris) dan `webapp.py` sudah di batas, dan semua fitur wajib bekerja 100% offline (PWA + Tauri, CSP `script-src 'self'`). ### ADR-038: dbconn — satu jalur koneksi SQLite, `isolation_level="IMMEDIATE"`, `write_tx` BEGIN IMMEDIATE, pagar AST
- **Date:** 2026-10-31
- **Agent:** Claude
- **Context:** 31 titik `sqlite3.connect` produksi tersebar (`webapp.get_db` 211 pemanggil, `TaskRepository._connect` 90 pemanggil, `_media_db_connect` untuk worker media/email, 27 blok `migrate_db`, `bot.py` `/link`) dengan pragma yang diulang dan tidak seragam (26 koneksi migrasi tanpa pragma sama sekali, 7 tanpa `row_factory`). PR B (loader plugin, `plugin_states`) menambah kode server `def` di threadpool sehingga penulisan benar-benar paralel dengan SQL di event loop. Diverifikasi (Python 3.12.3/SQLite 3.45.1 dan 3.13.18/3.53.1, hasil identik): baca-lalu-tulis tanpa transaksi eksplisit = pembaruan hilang tanpa error (2 thread × 50 increment → 50–51, bukan 100); transaksi *deferred* yang membaca lalu menulis setelah penulis lain commit gagal seketika `database is locked` (SQLITE_BUSY_SNAPSHOT, 0,0 s — `busy_timeout` tidak menolong); rebuild tabel (`RENAME TO x_old` → `CREATE` → `DROP x_old`) dengan FK ON menghapus baris tabel anak (CASCADE) dan menulis ulang `REFERENCES` anak ke `x_old` walau `legacy_alter_table=ON`. Bug pra-ada `/link <KODE>`: cabang token tidak pernah tercapai (guard `len(args) < 2`), `repo._db_path` (`AttributeError`), perbandingan `expires_at` naif vs ber-zona (`TypeError`). Spec `docs/superpowers/specs/2026-10-31-plugin-fase0b-design.md` §2 K1–K5, §4.2–4.3; rencana `docs/superpowers/plans/2026-10-31-plugin-fase0b-pr-a-dbconn.md`.
- **Decision:** (1) **Satu pintu koneksi** `dbconn.py` (stdlib saja; tidak meng-import `webapp`/`repository`/`bot`): `connect(path=None, *, foreign_keys=True, row_factory=sqlite3.Row)` = `sqlite3.connect(timeout=5.0, isolation_level="IMMEDIATE")` + `PRAGMA busy_timeout=5000` eksplisit, `journal_mode=WAL`, `foreign_keys=ON`/`OFF` eksplisit sesuai parameter; bila pragma gagal koneksi ditutup dulu lalu exception diteruskan. Mode transaksi **legacy** Python dipertahankan (`conn.autocommit` tidak pernah disentuh): SELECT/DDL sebelum DML pertama tetap di luar transaksi, DML pertama memicu `BEGIN IMMEDIATE` — jejak SQL endpoint lama identik kecuali kata `IMMEDIATE`. (2) `get_conn(path)` = semantik `get_db` (commit bila sukses, rollback bila `Exception`, selalu close); `webapp.get_db()` → `dbconn.get_conn(DB_PATH)` dan `TaskRepository._connect()` → `dbconn.get_conn(self.db_path)` sebagai pembungkus satu baris; `_media_db_connect()` → `dbconn.connect(DB_PATH)`; `bot.py` `/link` → `dbconn.get_conn(repo.db_path)`. **Path selalu eksplisit** dan dibaca saat dipanggil (`webapp.DB_PATH` bisa di-monkeypatch tes; `default_path()` = `config.DB_PATH` hanya untuk `plugin_host`/skrip). (3) **`write_tx(conn)`** = `BEGIN IMMEDIATE` eksplisit **sebelum** SELECT pertama, `COMMIT`/`ROLLBACK` (`BaseException`), `RuntimeError` bila transaksi sudah terbuka — **wajib untuk kode baru** yang membaca lalu menulis (K3); kode lama tidak di-refactor; `fetchall()` sebelum menulis pada koneksi yang sama. (4) **K4:** 27 koneksi `migrate_db` → `dbconn.connect(DB_PATH, foreign_keys=False)` kecuali blok project (`foreign_keys=True`; `PRAGMA foreign_keys=ON` lama dibiarkan) — rebuild tabel tetap tanpa FK. (5) **Pagar AST** `tests/test_dbconn_callsites.py`: `sqlite3.connect` (termasuk alias `import sqlite3 as X`, import di dalam fungsi, `from sqlite3 import connect`) hanya di `dbconn.py` (tepat satu); `isolation_level=`/`autocommit=` dan assignment atributnya dilarang di luar `dbconn.py`; pemanggil `dbconn.*` di `webapp`/`repository`/`bot` wajib path posisi; `migrate_db` wajib 27 × `foreign_keys=` literal dengan tepat satu `True`; dipindai akar repo + `plugins/*.py`; allowlist beralasan `merge_db.py`, `fix_list_tasks.py` (skrip sekali jalan); `scripts/` tidak dipindai. `tests/test_migrate_fk.py` menjaga FK OFF saat rebuild (baris anak utuh, `REFERENCES` tidak menjadi `drawings_old`). (6) Rilis tanpa versi SW/`whatsnew` (server saja); deploy wajib **restart manual `taskflow-web` dan `taskflow`** (workflow hanya `git reset` + `migrate_db`).
- **Consequences:** Bukti konkurensi (`tests/test_dbconn.py`): 2 thread × 50 increment baca-lalu-tulis tanpa `write_tx` → 50/51 dari 100 tanpa error; dengan `write_tx` → 100/100, 0 error; `write_tx` menunggu penulis lain lalu melihat tulisannya. 1250 tes lama lulus tanpa perubahan asersi (1284 total dengan 34 tes baru); satu tes lama (`tests/test_petakan.py` sisipan sinkron di dalam trace callback saat DELETE mulai) harus memindahkan titik sisipnya karena `BEGIN IMMEDIATE` sudah memegang kunci tulis di titik itu — asersi tidak berubah. `/link <KODE>` dari Pengaturan web baru benar-benar hidup (tiga bug diperbaiki + tes regresi); jalur token belum memindahkan task dari pengguna otomatis `tg_<id>` seperti jalur username (tindak lanjut). Kode plugin PR B memakai `host.get_conn()`/`host.write_tx` (ADR-039); menambah `sqlite3.connect` atau `autocommit` di luar `dbconn` gagal di CI. Tindak lanjut: `backfill_projects`/`backfill_contexts` memakai `SAVEPOINT` tanpa `BEGIN` → transaksi *deferred* (rawan BUSY_SNAPSHOT bila ada penulis lain saat deploy; hari ini hanya berjalan di `migrate_db`); `scripts/dedup_drawings.py` masih `sqlite3.connect` langsung; `PRAGMA foreign_keys=OFF` di dalam transaksi `webapp.py` (no-op pra-ada) dan audit kursor-terbuka-lalu-tulis tetap di luar cakupan (spec §12). Rollback = revert PR + restart dua layanan, tanpa perubahan data/skema.

Spec `docs/superpowers/specs/2026-10-31-plugin-fase0b-design.md` §2 K6–K18 (keputusan pemilik Q1 (a) keputusan terbaru menang, Q2 metrik Heatmap tetap per perangkat, Q3 teks UI, Q4 dua PR); rencana `docs/superpowers/plans/2026-10-31-plugin-fase0b-pr-b.md` R1–R19; fondasi koneksi ADR-038.
- **Decision:** (1) **Status per akun** di tabel `plugin_states(user_id, plugin_id, scope='user', enabled NULL|0|1, settings JSON ≤ 16 KB, updated_at)` (`plugin_states.py`); `enabled` NULL = ikut `defaultEnabled` `index.json`. **Last-write-wins di server** berdasarkan `updated_at` kiriman klien (waktu toggle) yang dipotong ke `min(klien, waktu server)` dan dibandingkan sebagai `datetime`; sama persis = diterapkan (idempoten); semua baca-lalu-tulis dalam `write_tx`. `GET /api/plugins/state`, `PUT /api/plugins/state/{id}` (`def`); `enabled` `StrictBool`, `settings: null` → 422; token clipper → 403 `PLUGIN_FORBIDDEN_TOKEN`. Urutan error PUT: pola id salah/`state` → 404 `PLUGIN_UNKNOWN`; indeks tidak sehat → 503 `PLUGIN_UNAVAILABLE`; id tak di indeks → 404 — indeks rusak (daftar kosong) tidak pernah membuat klien membuang toggle. (2) **Klien:** `TF.pluginstate` (`static/offline/pluginstate.js`) satu-satunya penulis cache `_meta`; toggle = satu transaksi `_meta` + `_outbox` dengan satu op `plugin_state/set` per plugin (coalescing; field yang tidak diubah tidak dikirim); pull di `sync()` sebelum `pushOutbox` (op tertunda menang); `ackPushed` tidak menimpa niat lebih baru. **Lebur pertama hanya untuk cache tanpa pemilik** (`plugins:state:owner:v1` tidak ada = cache 0a): OR(perangkat, server) dengan `updatedAt` asli 0a sehingga keputusan server yang lebih baru tetap menang (Q1a); pemilik berbeda → cache dan op lama dibuang, server diadopsi persis (status akun lain tidak pernah terbawa walau `clearAll` gagal). `syncpush`: 2xx → `ackPushed`; 404 `PLUGIN_UNKNOWN` → `dropOp`; 404 lain → tetap antre (jendela deploy); 4xx lain → `dropOp` + gagal. (3) **Peredaman lokal:** mati otomatis karena error → `_meta plugins:suppressed:v1 {reason, hash, at}` di perangkat itu saja; status efektif = akun ∧ ¬diredam; dihapus "Aktifkan lagi" atau `hash` plugin baru. (4) **Loader server** `plugin_loader.py` dipakai web dan bot: indeks bersama `static/plugins/index.json`, `importlib` per `plugins/<id>.py` (`_*` dilewati) sebagai `alurik_plugins.<id_>`; plugin ditolak utuh bila memakai simbol yang belum didukung (`on_task_written`, `jobs`, `register_bot`, `intake`), router ber-prefix, atau endpoint `async def` tanpa `@host.allow_async`; satu plugin rusak tidak pernah menjatuhkan web, bot, atau `migrate_db`; log `alurik.plugins` `plugin server: N dimuat, M ditolak`. Fasad `plugin_host.py` (`HOST_API = 1`: `current_user`, `get_conn`, `write_tx`, `now_utc`, `allow_async`) di-bind web/bot. (5) **`migrate()` berpagar:** `migrate_db` mendapat satu baris `plugin_loader.migrate(DB_PATH)` setelah blok project (pagar 27 `dbconn.connect` PR A tidak berubah); loader membuka koneksi FK OFF sendiri; `ensure_schema` tiap plugin dalam `write_tx` lewat koneksi pembungkus yang menolak `commit`/`rollback`/`close`/`executescript`; selisih `sqlite_master` (lewati `sqlite_%`): setiap objek baru/berubah/hilang wajib bernama **dan** ber-tabel induk `plg_<id_>_`; `PRAGMA foreign_key_check` per tabel plugin yang tersentuh (bukan seluruh DB, agar pelanggaran FK pra-ada tidak menggagalkan plugin). Gagal → rollback, `schema_failed`, rute 503. (6) **Router** dipasang di `/api/plugins/<id>` dengan `Depends(current_user)` + `Depends(require_plugin_enabled(id))` (`def`): clipper 403, tidak sehat 503, nonaktif 403 `PLUGIN_DISABLED`. (7) **`TF.api.fetch`** (izin `network`, `apiVersion` tetap 1): hanya ke `/api/plugins/<id>/…`, lewat `api.fetch` host yang disuntik `bindHost({fetch, isOfflineErr, pushNow})`; offline → `PluginNetworkError` `"Butuh koneksi internet"` tanpa request; menunggu push toggle tertunda ≤ 5 s; `PluginNetworkError` tidak dihitung error plugin; `api.fetch` selalu ada di `api`, tanpa izin → `PluginPermissionError`. Lint `compile.js`: `fetch(` polos dan `window|self|globalThis.fetch` tetap ditolak, `.fetch(` hanya dengan izin `network`; id `state` dicadangkan. (8) **Bot:** error handler `on_error` — `telegram.error.NetworkError` (termasuk `TimedOut`, juga dari polling) = satu baris WARNING tanpa traceback, selain itu ERROR + traceback.
- **Consequences:** Plugin yang dinyalakan ikut ke perangkat lain setelah sinkron, tetap bisa diubah offline, dan tidak ada toggle yang hilang selama jendela deploy atau saat indeks server rusak. Setiap perubahan kode server plugin butuh **restart manual `taskflow-web` dan `taskflow`** (workflow deploy hanya `git reset` + `compile` + `migrate_db`). Status tidak disiarkan lewat SSE: perangkat lain dan tab lain di browser yang sama melihat perubahan pada sinkron/reload berikutnya. Kolom `settings` disimpan dan disinkron tetapi belum diekspos ke plugin (`api.settings` Fase 1); `plugin_states` belum ikut ekspor data. Rilis SW `taskflow-v490-plugin-akun`. Rollback = revert sebagai rilis baru (SW bump + whatsnew `silent`) + restart dua layanan; tabel `plugin_states` dibiarkan; op `plugin_state` di klien lama dibuang oleh fallback `processOp` untuk op tak dikenal (tidak ada antrean macet).
- **Batas diketahui (review akhir PR B):** pagar 0b **bukan sandbox**. Lint `compile.js` berbasis teks dan bisa diakali (`globalThis["fetch"]`, alias, `WebSocket`, `EventSource`, `import()`); `plugin.js` berjalan di halaman host. Pagar `ensure_schema` hanya menangkap DDL tak sengaja di luar prefix `plg_<id_>_` — tidak menahan `DELETE`/`UPDATE` ke tabel host, `ATTACH`, atau trigger `plg_` yang menulis tabel host — dan endpoint plugin memakai koneksi host yang sama. Plugin saat ini hanya bawaan yang direview manusia; sandbox (`set_authorizer`, Worker/iframe ber-origin terpisah) ditunda sampai ada plugin pihak ketiga. Perbaikan dari review: `api.fetch` menolak karakter kontrol dan mewajibkan pathname hasil normalisasi `new URL` sama dengan path asli dan tetap di bawah `/api/plugins/<id>` (sebelumnya `/.\t./` lolos cek lalu dilipat parser menjadi `/api/tasks`); `PUT /api/plugins/state/{id}` membaca ulang `index.json` sekali sebelum 404 `PLUGIN_UNKNOWN` (gagal baca → daftar lama dipertahankan); runtime mengabaikan cache yang `owner`-nya ≠ `userId` ter-bind (default `index.json`) sampai pull menulis owner yang benar. `webapp.py` tidak memanggil `logging.basicConfig`, jadi baris INFO `plugin server: …` hanya terlihat di log bot; WARNING/ERROR loader tetap terlihat di web.

### ADR-041: Record plugin (`plugin_records`) dengan kursor `seq`, IndexedDB v7, `api.records`
- **Date:** 2026-11-01
- **Agent:** Claude
- **Context:** Plugin Fase 1 (Timeline/Gantt, kalender, preset) butuh data yang berdiri sendiri (bukan per task) dan ikut sinkron, offline, serta berbagi workspace; `tasks.ext` (ADR-040) hanya untuk data per task. Spec Fase 1 B5–B9 menetapkan tabel server, store IndexedDB, dan op `plugin` di outbox, tetapi beberapa asumsi Lampiran A/B tidak tahan uji: (1) `updated_at` record = **waktu edit klien**, sehingga kursor keyset `(updated_at, id)` (Lampiran A #2) melewatkan edit offline yang terlambat terkirim (perangkat lain sudah melewati `updated_at` itu); (2) `pluginstate.setLocal` memindai seluruh `_outbox` (`pluginstate.js:107–117`) dan `outbox.js` tanpa indeks, sehingga coalescing per record tidak boleh meniru pola itu; (3) anggota baru atau yang keluar dari workspace mengubah himpunan record yang boleh dilihat, yang tidak terlihat di kursor biasa; (4) boolean bukan kunci IndexedDB yang sah (indeks `dirty`/`deleted` perlu 0/1).
- **Decision:** K3, K8–K11 spec dan R1–R19 rencana PR 1a-2. **Server** (`plugin_records.py`, tabel host, bukan `plg_*`): skema persis §5.2 (PK `(plugin_id, entity, owner_key, id)`, `CHECK ((user_id IS NULL) <> (list_id IS NULL))`, `ux_plugin_records_seq`, indeks parsial per user/list, `plugin_records_meta`); skema dibuat `plugin_loader.migrate` (kegagalan di-log dan dipetakan ke 503 `PLUGIN_UNAVAILABLE` agar op klien tetap antre); rute `GET`/`POST /api/plugins/{id}/records` dicadangkan host dan **tidak mensyaratkan plugin ON** (push selalu; hanya token sah, bukan clipper, plugin di indeks dan berizin `records`, entitas dideklarasikan). **Kursor `seq`**: `seq` diberikan di dalam `write_tx` yang sama dengan tulisnya (`max(MAX(seq), purged_seq) + 1`, tidak dipakai ulang setelah purge tombstone teratas); kursor `"1.<seq>.<fp>"` dengan `fp` = **sidik jari keanggotaan** (daftar id workspace yang bisa diakses) — `fp` berbeda, `seq < purged_seq`, atau format rusak → `{"reset": true}` dan klien menarik penuh. **LWW**: `base_version` + idempotensi kiriman ulang; `min(updated_at klien, now)` melawan `updated_at` baris; kalah → `applied: false` + baris server; id sama di scope lain yang terlihat pengguna → `SCOPE_IMMUTABLE`; tombstone 30 hari. **Klien**: IndexedDB `taskflow-offline` **v7** (`plugin_records` keyPath `[plugin_id, entity, id]` dengan indeks `entity`, `entity_updated`, `entity_dirty`, `entity_scope`; `plugin_kv`) di `PLUGIN_STORES` terpisah dari `ENTITY_STORES`; `dirty`/`deleted` 0/1; `static/offline/plugin_sync.js` (`TF.pluginsync`): tulis lokal = satu transaksi `["plugin_records", "_outbox"]`, **satu op per record** lewat `op_qid` (hapus op lama O(1), tanpa memindai outbox), `pushOp` memakai record terkini dan **CAS** `op_qid` (edit selama POST terbang tidak hilang, `applied: false` tidak menimpa edit yang lebih baru), `remove` = tombstone lokal sampai ack, `$task` lewat `resolveExtRefs`/`rewriteTaskRefs` (K7, `updated_at` tidak berubah), pull per plugin ON dengan kursor di `plugin_kv`, **sapu setelah tarik penuh** (record bersih ber-`sync_gen` lama dihapus; record `dirty` diberi `sync_gen` agar tidak tersapu bila push-nya tidak mendapat `seq` baru), penjaga pemilik cache saat ganti akun, heal record `dirty` terdampar. **`api.records`** (`get`/`list`/`put`/`remove`/`onChange`/`newId`) dan izin `records` + `manifest.records` (`conflict: "lww"`, `maxBytes` ≤ 64 KB, ≤ 16 entitas; aturan sama di `compile.js` dan runtime, vektor bersama `tests/fixtures/plugin_records_vectors.json`); galat entitas tak dideklarasikan/ukuran/scope → `PluginStorageError` ber-`code`, tanpa izin → `PluginPermissionError`; `apiVersion` tetap 1; plugin OFF tetap push tetapi tidak pull; ekspor akun memuat `plugin_records.json`. **Penyimpangan dari Lampiran B7:** indeks parsial `seq` (`ux_plugin_records_seq` + indeks per user/list) menggantikan `(user_id, plugin_id, entity, updated_at, id)`.
- **Consequences:** Plugin bisa menyimpan record sendiri yang ikut sinkron dan workspace, bekerja offline sejak rilis terpasang, dan edit offline lama tetap tertarik perangkat lain (urutan commit server, bukan jam klien). IndexedDB naik ke v7 **sekali dan tidak pernah turun**: revert = rilis baru yang mempertahankan `DB_VERSION = 7` dan `PLUGIN_STORES`; op `plugin` di klien hasil revert dibuang fallback `processOp` di `syncpush.js` (cabang tanpa penanganan → `TFoutbox.outboxRemove(op.qid)`), jadi record yang belum terkirim hilang — dapat diterima karena sebelum PR 1b praktis belum ada data nyata; tabel `plugin_records` dibiarkan. Perubahan keanggotaan workspace memicu tarik penuh per plugin ON. LWW memakai waktu klien (dipotong ke waktu server) sehingga rentan selisih jam perangkat; konflik record belum tampil di bilah konflik (hanya `error`/`lost` ke plugin). Id deterministik harus menyandikan scope atau memakai `newId()`. `api.records.onChange` juga memancarkan sinyal aditif `{entity: null, ids: [], source: "sync", pulled: true}` tepat satu kali saat tarik record satu plugin selesai dan sukses (halaman `more: false`; bukan saat galat, `PLUGIN_UNKNOWN`, batas 50 halaman, atau reset kedua; statistik `pullAll` memuat `complete`), supaya konsumen tahu data bersama sudah termuat tanpa mengandalkan `sync.done` (menyala juga saat gagal) atau event `source: "sync"` dari ack push/`rewriteTaskRefs`; `apiVersion` tetap 1. Batas yang diketahui: (a) ack push yang mendarat di antara halaman terakhir tarik penuh dan sapu bisa menyembunyikan record sebentar sampai tarik delta berikutnya; (b) pemeriksaan `SCOPE_IMMUTABLE` hanya mencari `id` yang sama pada kunci pemilik yang bisa diakses pengguna (`owner_key IN ('u:<uid>', 'l:<id>' per workspace yang bisa diakses) AND owner_key != <pemilik item> AND id = ?`, lewat `json_each`), memakai PK penuh `(plugin_id, entity, owner_key, id)` sehingga tanpa pemindaian baris pengguna lain; (c) tab pra-1a-1 tetap bisa menahan upgrade v7 (tab baru menampilkan banner `blocked` dan lanjut sendiri setelah tab lama ditutup), karena itu merge menunggu ≥ 3 hari setelah 1a-1 ter-deploy. Setiap deploy butuh **restart manual `taskflow-web` dan `taskflow`**; selama jendela deploy server lama menjawab 404 tanpa kode dan op record tetap antre. Rilis SW `taskflow-v494-plugin-records`, whatsnew `silent`, `app.css?v=383` tetap.

Toast kalah LWW juga dari seksi Jadwal (tanpa view Gantt), dengan dedupe per id kalender 1,5 s agar view + panel Live Edit = satu toast. (13) **CSS:** hanya `.plg-timeline-*` dengan pengubah `.is-*` yang menempel pada kelas plugin, token tema saja, dan satu pembacaan atribut host `[data-theme="dark"]` hanya untuk `color-scheme` input tanggal (didokumentasikan di README §8 sebagai pengait baca-saja yang diizinkan). - **Consequences:** Pengguna yang menyalakan Timeline mendapat Gantt per project/workspace dengan hari kerja Indonesia tanpa jaringan. **Data libur wajib diperbarui tiap tahun** — butir baru PROTOCOL §4 nomor 6 ("Sejak Oktober: SKB … tahun berikutnya sudah masuk `holidays-id.js`?"); tanpa itu tahun baru tampil tanpa libur nasional dengan catatan di bawah legenda. **Mode Manual tidak memindahkan task**: dependensi hanya menandai pelanggaran; jadwal otomatis, CPM/jalur kritis, baseline, dan batasan = PR 1c. **Seret = satu PUT task per task**; PUT yang hanya membawa `ext_patch` (seret Timeline, edit seksi Jadwal) **tidak** mengirim notifikasi "memperbarui task" ke anggota workspace (K6/R6, ADR-040; `webapp.py` `ext_only`); sebuah PUT baru memberi notifikasi bila ia juga membawa perubahan field inti yang nyata (mis. edit offline tertunda yang ikut terkirim dalam op yang sama), dan itu paling banyak sekali per aktor per task per 10 menit (R20). **Kalender workspace diubah semua anggota** (LWW per record utuh; edit yang kalah memberi toast; anggota yang Timeline-nya OFF tidak terpengaruh dan tidak menimpa field plugin berkat patch per kunci ADR-040). Task yang jadwalnya jauh (> ~5 tahun dari hari ini) tidak terlihat di grafik. `index.html` **+0 baris** (hanya string versi SW), tidak ada berkas `static/offline/` baru, tidak ada perubahan server/skema. **Deploy tanpa restart:** tidak ada perubahan server di 1b dan D6 terpenuhi (server membaca ulang `index.json` sekali sebelum menjawab 404 `PLUGIN_UNKNOWN`), sehingga edit kalender di jendela deploy tidak hilang dan `taskflow-web` tidak perlu direstart (restart 1a-2 tetap berlaku untuk PR #120). **Rollback** = matikan plugin di Pengaturan › Plugin, atau revert sebagai rilis baru (naikkan SW + whatsnew `silent`); data `timeline.*` di `tasks.ext` dan record `calendar` dibiarkan (tidak dihapus) sehingga menyalakan lagi memulihkan jadwal. Risiko terbuka: seret sentuh dengan tekan lama belum diuji di perangkat nyata (emulator tidak membedakan), `touchmove` non-pasif mungkin menimbulkan gulir patah — periksa di ponsel.

### ADR-043: Push task "ext saja" (`ext_only_rev`), `setMany` satu render, entitas record baru tanpa restart
- **Date:** 2026-11-01
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-11-01-plugin-fase1-1c-otomatis-design.md` (K23–K26), rencana `docs/superpowers/plans/2026-11-01-plugin-fase1-pr-1c-0.md` (R1–R20). Push task selalu mengirim seluruh field inti dari salinan lokal (`taskToUpdatePayload`), server tidak punya LWW untuk task, `schedulePush`/`__pushNow` mendorong tanpa menarik dulu, dan LWW di pull memenangkan edit ext lokal yang "lebih baru" atas nilai server. Akibatnya menyeret bar Timeline di perangkat yang datanya basi mengembalikan judul/status yang baru diubah anggota lain (sudah ada sejak 1b; 1c melipatgandakan frekuensinya). `setMany` memperbarui state host per item (satu render per item di bawah `ReactDOM.render` legacy). Entitas record baru di `manifest.records` butuh restart server karena `INVALID entity` dibuang permanen oleh klien.
- **Decision:** (1) **Penanda `ext_only_rev` (R1–R2, K25):** angka yang diikat ke `rev` (bukan boolean, karena tab lama berbagi IndexedDB dan menyalin record). `TF.taskext.extOnlyNow(rec)` = kotor, tidak dihapus, `ext_only_rev === rev`; satu-satunya pembaca. Patch ketat (`ext_patch` objek polos dan kunci lain `undefined`); semua penulis yang mengubah field inti menaikkan `rev` sehingga penanda batal otomatis. Audit penulis store `tasks` (R9) dikunci tes pagar `taskext_writers_fence` (entri AUDIT untuk setiap penulis baru). (2) **Bentuk payload diputuskan saat kirim (R3–R4):** `opUpdate` mengirim `{ext_patch}` saja bila `extOnlyNow`, selain itu payload penuh persis seperti sebelumnya (snapshot T5). Op `update` untuk record bersih dibuang tanpa request. (3) **Adopsi inti dari respons PUT ext saja (R5):** `markPushed` menerima `adoptAny` (`TF.hydrate.coreFromServer`) agar perangkat basi menampilkan nilai server. (4) **Pull (R7, R11):** inti server menang bila `extOnlyNow(localRec)`, kunci ext lokal ditempel kembali dan op diantre ulang. (5) **Hapus tag (R8):** `removeEntityTag` menaikkan `rev` bila penanda sah; syarat spec "tanpa baris `entity_tags` kotor" diganti karena `entity_tags.dirty` tidak pernah dibersihkan. `syncconflict` `discard_local` menghapus penanda (R10). (6) **K24 `setMany` (R11–R12):** `patchTaskExt` tepat sekali per item di dalam satu `ReactDOM.unstable_batchedUpdates`, lalu tulis berurutan, berhenti pada gagal pertama, satu `refreshTasks`; penolakan membawa `err.applied`; `apiVersion` tetap `1`. (7) **K26 server (R13):** `plugin_records._decl_for` membaca ulang indeks plugin untuk entitas yang valid tetapi belum dikenal, paling sering sekali per 10 detik (TTL proses-global, `_decl_clock` bisa disuntik), di luar transaksi tulis, daftar lama bertahan bila indeks rusak, nama tak sah tidak memicu. Server PUT task tidak berubah (R14); tanpa endpoint batch (K23).
- **Consequences:** Edit ext tidak pernah lagi membawa field inti; perangkat basi melihat nilai server setelah push pertamanya; PUT lebih sedikit (op basi dibuang). 1c-1/1c-2/1d dideploy statis tanpa restart; rilis ini butuh restart **`taskflow-web` saja** (bot tidak meng-import `plugin_records`). Jendela deploy aman ke dua arah (R15). Verifikasi pasca-restart (probe saja **tidak** membedakan proses lama dan baru: keduanya menjawab `INVALID`/`entity`): (a) wajib — `systemctl show -p ActiveEnterTimestamp taskflow-web` **lebih baru dari waktu selesai deploy** (workflow tidak me-restart); (b) opsional — `POST /api/plugins/timeline/records` dengan item entitas `probe` → `INVALID`/`entity`, lalu `journalctl -u taskflow-web` memuat baris **WARNING** "plugin_records: entitas probe belum dideklarasikan timeline → baca ulang indeks" (hanya kode baru yang mencetaknya; satu baris per baca ulang, paling sering 1×/10 detik per proses — probe kedua dalam 10 detik tidak menambah baris). Urutan wajib: merge + deploy + restart 1c-0 → verifikasi → baru merge 1c-1 (1c-1 memakai record `project` yang bergantung K26); rollback 1c-0 setelah 1c-1 dilarang tanpa rollback 1c-1 dulu. Rollback = rilis baru (SW bump + whatsnew `silent`) + restart; kunci `ext_only_rev` diabaikan kode lama, tanpa data hilang atau skema berubah. Server **harus tetap di 1a-1 (#119) atau lebih baru** (rollback 1c-0 maupun server mana pun): di bawahnya PUT `{ext_patch}` saja dari klien 1c-0 dijawab 400 dan berakhir di `sync_error` yang tidak bisa dipulihkan dengan "Coba lagi". Tab lama tetap mengirim payload penuh sampai diperbarui. **Residual yang diterima:** (R2) PUT ext saja tetap menaikkan `tasks.updated_at` di server, sehingga edit inti offline yang lebih tua dari perangkat lain kalah saat tarik; tindak lanjut "LWW per kelompok field task". (R8) penghapusan tag pada task yang hanya punya edit ext tertunda menaikkan `rev` (penanda batal) sehingga segera terkirim lewat PUT penuh; penghapusan tag baru tertunda sampai PUT penuh berikutnya hanya untuk task bersih, bila PUT penuh task itu sedang terbang (tag dibaca saat payload dibuat), dan pada jalur pull R11 (yang menyetel ulang penanda); utang sinkron tag pra-ada (pull task tidak menarik tag; PUT penuh dari perangkat tanpa tag lokal menghapus tag server). PUT penuh susulan (R8) bisa membawa inti basi (R2). `setMany`: jendela optimistis saat gagal di tengah — item yang belum tersimpan menampilkan nilai baru sampai `refreshTasks` selesai (dan bila `refreshTasks` gagal, sampai muat ulang berikutnya). Baca ulang indeks K26 memakai TTL proses-global 10 detik (satu proses = satu jendela throttle untuk semua plugin). Konvensi tes pagar: setiap penulis baru store `tasks` wajib masuk daftar AUDIT di `taskext_writers_fence.test.js` beserta penanganannya; pagar tidak menangkap alias hasil destrukturisasi atau kunci terhitung (batas leksikal). **Diperbaiki pada review akhir:** `adoptCore` (respons PUT ext saja) tidak mengadopsi inti bila `base_rev` terkini lebih baru dari `updated_at` respons (pull tab lain sudah mengadopsi revisi anggota lain selama request; `markPushed` juga tidak memundurkan `base_rev`) — sebelumnya inti respons basi menimpa nilai itu dan edit inti berikutnya membalik edit anggota lain di server. Pull (R7) untuk record ext saja hanya memenangkan server bila daftar tidak lebih tua dari `base_rev`; daftar basi → lokal tetap sampai pull/respons push berikutnya. `_decl_for` dalam jendela throttle memakai deklarasi proses saat ini (`plugin_loader.records_decl`, tanpa baca berkas), bukan salinan `_guard` yang bisa basi.

### ADR-044: Waktu inti task terikat `updated_at` (`core_updated_at`); tarik memenangkan inti lokal bila inti server tidak berubah
- **Date:** 2026-11-04
- **Agent:** Claude
- **Context:** Spec/rencana `docs/superpowers/plans/2026-11-01-plugin-fase1-pr-1c-0b.md` (K45–K49, R1–R5, R11). Residual R2 ADR-043: PUT "ext saja" tetap menaikkan `updated_at` task di server, dan tarik memakai LWW satu record, sehingga edit inti offline yang lebih tua dari seret/Terapkan Timeline perangkat lain kalah dan hilang (direproduksi di baseline). S9: cap waktu server memakai `datetime.now()` naif; bila zona waktu server bukan UTC, server tampak lebih baru (mis. 7 jam) dari cap klien. Pada produksi saat ini VPS memakai Etc/UTC (dikonfirmasi pemilik 2026-11-04), jadi S9 **laten, tidak aktif di produksi**; hanya muncul bila TZ berubah atau di lingkungan dev. Ada 12 penulis `updated_at` lintas web/bot.
- **Decision:** (1) Dua kolom mentah `ext_core_at`/`ext_only_at` terikat ke `updated_at` (K45); field API `core_updated_at` sengaja berbeda nama dari kolom mentah (K47). (2) Pembekuan hanya untuk PUT ext murni, dihitung di SQL (K46). (3) Field API diberi nama berbeda dari kolom mentah (K47). (4) Migrasi tanpa backfill (K45/R4). (5) Aturan tarik (K48): (1) bandingkan cap waktu server saja (inti server tidak berubah sejak sinkron terakhir perangkat), lalu (2) LWW memakai waktu inti. (6) Klien hanya mengubah `syncpull.js`; tanpa perubahan IndexedDB, payload, atau K6. Jawaban Q1 (a): penghapusan offline tetap terhapus.
- **Consequences:** Edit inti offline tidak lagi hilang karena seret/Terapkan Timeline perangkat lain (termasuk penghapusan, sesuai Q1); daftar tarik basi tidak lagi menimpa edit inti tertunda (efek samping baik). Penulis server baru otomatis benar selama menaikkan `updated_at` dengan `datetime.now().isoformat()` (pagar `test_task_core_time`). PUT penuh dari klien lama tidak dibekukan. Rilis butuh restart `taskflow-web` (bot tidak); verifikasi `core_updated_at` ada di respons. Rollback = rilis baru + restart, kolom dibiarkan. Residual: konflik inti sungguhan tetap LWW yang dipengaruhi S9 (laten); aturan (1) mengasumsikan jam server tidak mundur (asumsi sama dengan `markPushed`; Etc/UTC tanpa DST); edit ext lokal tetap memajukan `updated_at` lokal (R7); tag (R8 1c-0) tetap; ekspor `tasks.json` menyertakan kolom mentah (tanpa pembaca, didokumentasikan, tidak diubah); PUT inti-noop (nama project sama / id basi) tetap membeku (aman); penghapusan Q1(a) diuji di tingkat pull saja. Residual: (a) quadrant pada PUT ext murni dihitung ulang dari `existing` basi (pra-1c-0, field turunan, cron memperbaiki). (b) Edit inti yang dibuat saat PUT ext-only 1c-0 sedang berjalan memajukan `base_rev` tanpa mengadopsi inti server, sehingga seret oleh perangkat ketiga kemudian mencapai aturan (1) dan PUT penuh A diterapkan sebagai LWW satu record menurut urutan waktu nyata (dapat diterima; sebelum PR ini edit A biasanya malah terbuang). Catatan terpisah, bukan bagian PR ini: 500 yang sudah ada di `PUT` dengan `recurrence_type` valid (`sqlite3.Row.get`) perlu perbaikan sendiri.

### ADR-048: Checklist bertingkat — progress dan `checklist_total` sebagai field turunan server
- **Date:** 2026-11-09
- **Agent:** Claude (Opus 5.5)
- **Context:** Spec `docs/superpowers/specs/2026-11-06-checklist-bertingkat-design.md` (K1 hanya level atas yang dihitung, K2 slider terkunci, K5/K7 centang dan hapus berantai, K15 hitung ulang task lama, K17 dampak Timeline diterima; D1–D3) dan rencana `docs/superpowers/plans/2026-11-09-checklist-bertingkat-pr-a-server.md`. Checklist bisa diubah oleh anggota workspace lain kapan saja. Bila setiap centang menaikkan `tasks.updated_at`, anggota yang sedang mengedit task itu offline akan terkena konflik sinkron. Di sisi lain, `syncpush.js` selalu mengirim `progress` di setiap PUT task, sehingga salinan lama bisa menimpa angka dari checklist.
- **Decision:**
  - `subtasks.parent_id` (NULL = level atas, tanpa FK) menyimpan pohon; logika pohon murni di `checklist_tree.py` (pre-order iteratif, siklus diputus pada anggota `(sort_order, id)` terkecil). Semua aturan tulis (penomoran ulang saudara, centang/hapus berantai, hitung progress) ada di `TaskRepository`, satu `dbconn.write_tx` per operasi, sehingga web dan bot sama.
  - Setiap operasi tulis checklist memulihkan dulu pohon task itu (`_heal_task_tree`: butir yatim/lintas task/siklus → level atas sesuai pohon tampil); baca mengembalikan `parent_id` efektif.
  - `tasks.progress` dan kolom baru `tasks.checklist_total` adalah **field turunan server**: ditulis bersama operasi checklist dan oleh `heal_checklists()` di setiap `migrate_db()`/start, **tanpa** menaikkan `updated_at`, hanya bila nilainya berubah. Persen = `(done*200 + total) // (2*total)` (setengah ke atas; vektor bersama `tests/fixtures/checklist_percent_vectors.json` untuk klien).
  - `PUT /api/tasks/{id}` mengabaikan `progress` selama task punya butir checklist; PUT yang hanya membawa `progress` terabaikan → 200 tanpa UPDATE (tanpa `updated_at`, tanpa notifikasi).
- **Consequences:**
  - Klien PR B wajib mengambil `progress`/`checklist_total` lewat `TASK_DERIVED` (`syncpull.js`), karena perubahannya tidak menaikkan `updated_at`.
  - Jendela PR A → PR B (klien SW v500 + server baru), dibuktikan E2E `temporary_files/e2e_checklist_pr_a.py`: persen baru dari checklist (centang/tambah/hapus, termasuk hitung ulang migrasi) **tidak sampai ke perangkat yang sudah menyimpan task itu** sampai PR B atau ada edit lain yang menaikkan `updated_at`; hanya perangkat dengan penyimpanan lokal kosong yang melihatnya. Bagi pengguna ini sama dengan sekarang (progress belum mengikuti checklist), tetapi angka bisa berbeda antar perangkat — alasan PR B di-deploy segera setelah PR A.
  - Pada jendela yang sama, slider Progress yang digeser pada task bercheklist tampak tersimpan tetapi angkanya **tertinggal di perangkat itu** (respons PUT dan pull tidak mengadopsi `progress` karena `base_rev` maju) sampai PR B atau ada edit lain pada task itu; server dan perangkat lain tetap memakai angka checklist. Payload penuh yang hanya berbeda di `progress` tetap menaikkan `updated_at` dan bisa memicu satu notifikasi "memperbarui task" (dibatasi R20). Klien lama juga tidak melihat angka hasil hitung ulang migrasi sampai PR B.
  - K17: butir level atas tercentang (termasuk hasil hitung ulang migrasi) membuat Timeline menganggap task sudah mulai (`progress > 0`).
  - Deploy: **cadangkan `taskflow.db` (`./backup.sh`) SEBELUM merge** — push ke `main` langsung menjalankan `migrate_db()` lewat workflow, dan hitung ulang K15 menimpa `progress` manual task lama bercheklist (revert tidak mengembalikannya). Sesudah workflow: `sudo systemctl restart taskflow taskflow-web` (bot lama yang masih jalan menghapus tanpa berantai).
  - Rollback: revert PR A sebagai rilis baru; kolom `parent_id`/`checklist_total` dibiarkan (kode lama mengabaikannya). Kode lama mengurutkan butir menurut `sort_order` per task saja, sehingga kelompok saudara bercampur (anak bisa tampil sebelum induknya); centang tidak berantai, hapus induk meninggalkan anak yatim, dan PUT `progress` kembali diterima. Deploy ulang PR A memulihkan yatim ke level atas lewat `heal_checklists`. Nilai `progress` manual sebelum PR A hanya kembali dari cadangan.
  - Residual: id di path > 2⁶³ masih 500 (pra-ada di seluruh API); idempotensi `client_id` di `add_subtask` tidak dibatasi per task (pra-ada); pengecekan "punya checklist" di PUT berjalan sebelum transaksi tulis (jendela milidetik, dipulihkan operasi checklist berikutnya / start).

### ADR-051: Checklist Fase 2 — `checklist_rev` sebagai field turunan, centang set, sinyal `rev_bumped`
- **Date:** 2026-11-11
- **Agent:** Claude (Opus 5.5)
- **Context:** Spec `docs/superpowers/specs/2026-11-11-checklist-offline-fase2-design.md` (F1 semua checklist offline, F5 pendekatan A antrean aksi, E1–E7) dan rencana `docs/superpowers/plans/2026-11-11-checklist-offline-pr-a2-server.md`. Klien local-first (PR B2) perlu tahu checklist task mana yang berubah tanpa mengunduh semuanya, perlu mengirim ulang aksi dengan aman setelah koneksi putus, dan perlu tahu kapan versi lokalnya boleh dimajukan tanpa mengambil ulang. Toggle membalik status sehingga tidak aman diulang. ADR-050 dipesan rencana PR 1d-2, jadi keputusan ini memakai ADR-051.
- **Decision:**
  - `tasks.checklist_rev` (field turunan seperti `progress`/`checklist_total` di ADR-048): naik tepat 1 per transaksi tulis checklist yang mengubah sesuatu, +1 tersendiri bila `_heal_task_tree` memulihkan pohon, 0 untuk no-op; tanpa `updated_at`. `migrate_db`/`heal_checklists` mengisi 1 untuk task lama bercheklist (`rev_init`). `merge_db.py` menaikkan rev task penerima butir.
  - `task_progress` mendapat `rev` dan `rev_bumped` (operasi ini sendiri — bukan pemulihan — menaikkan rev). Aturan klien: rev tersimpan dimajukan hanya bila `rev_bumped` dan `rev` = tersimpan + 1; `rev` = tersimpan → tetap; selain itu dikosongkan (ambil ulang).
  - `PATCH /api/subtasks/{id}` menerima `title` dan/atau `is_done` (set; `true` berantai ke turunan) dalam satu transaksi — dipakai antrean klien sebagai pengganti toggle.
  - `GET /api/checklists?task_ids=` (≤ 200, baca saja, akses setara `_can_access_task` lewat satu kueri, `def` di threadpool).
  - Idempotensi tambah per task; `client_id` yang bertabrakan dengan task lain disimpan berprefiks `"<task_id>:"` (indeks unik global `idx_subtasks_client_id` tidak diubah).
- **Consequences:**
  - Aplikasi v502 tidak terpengaruh (field tambahan diabaikan; `PATCH {title}` dan toggle tetap; E2E `e2e_checklist_tree.py` 152/152 terhadap server baru).
  - PR B2 mengambil `checklist_rev` lewat `TASK_DERIVED` dan mengunduh lewat batch; aturan majukan rev memakai `rev_bumped`.
  - Rollback: revert sebagai rilis baru; kolom `checklist_rev` dibiarkan (kode lama mengabaikannya). `client_id` berprefiks tetap unik secara global.
  - Deploy: cadangkan `taskflow.db` sebelum merge (migrasi mengisi `checklist_rev`), lalu `sudo systemctl restart taskflow taskflow-web`.
