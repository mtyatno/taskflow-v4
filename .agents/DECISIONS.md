### ADR-004: Note Trash via snapshot table `trashed_notes` (bukan kolom `deleted_at`)
- **Date:** 2026-10-02
- **Agent:** Claude
- **Context:** Fitur Sampah note butuh hapus yang bisa dipulihkan 30 hari. ±30 query di `webapp.py` membaca `scratchpad_notes` (list, search, titles, backlinks, halaman publik, export, bot); soft-delete lewat kolom memaksa semua query difilter dan satu yang terlewat membocorkan note terhapus.
- **Decision:** Hapus tetap menghapus dari `scratchpad_notes` (cascade lama tidak berubah), tetapi dalam transaksi yang sama menulis snapshot JSON (semua kolom + tag + pin + publish + lampiran) ke `trashed_notes`. Restore memasukkan kembali dengan id asli. Purge lazy setelah `NOTE_TRASH_RETENTION_DAYS = 30`. Endpoint `/api/scratchpad/trash*` hanya online (router lokal & SW tidak melayaninya). Spec: `docs/superpowers/specs/2026-10-02-note-trash-design.md`.
- **Consequences:** Query lama tidak tersentuh. Klien: setelah restore buang op outbox `delete` tertunda (`noterepo.discardPendingDelete`) dan pull memperbarui `linked_to_cids` basi. Keterbatasan: perangkat lain yang mengedit note saat note dihapus membuat salinan baru (POST setelah PUT 404) → setelah restore ada 2 note. File lampiran Nextcloud tidak dibersihkan saat hapus permanen (perilaku lama). Deploy wajib restart service agar `migrate_db()` membuat tabel.

### ADR-005: Pesan Pribadi (DM) di tabel terpisah, tanpa ikatan ke shared list
- **Date:** 2026-10-03
- **Agent:** Claude
- **Context:** Diskusi hanya mendukung chat grup (`messages.list_id`). Pemilik produk ingin DM 1-on-1; memulai hanya dengan sesama anggota grup (anti-spam), tetapi percakapan tetap aktif walau keduanya tidak lagi satu grup.
- **Decision:** Tabel baru `dm_conversations` (pasangan ternormalisasi `user_a < user_b`, UNIQUE), `dm_messages`, `dm_reads` (penanda baca per user = `last_read_id`). Cek berbagi grup hanya saat membuat percakapan baru; akses berikutnya hanya cek peserta (404 untuk selainnya). Tidak ada FK ke `shared_lists`. Endpoint `/api/dm/*` online-only (SW network-only, tidak ada rute lokal, tidak memakai chatrepo). Notifikasi in-app ditahan bila penerima subscribe SSE percakapan (`dm_subscribers` menyimpan `(user_id, queue)`), dan tidak diduplikasi selama notifikasi identik belum dibaca. Spec: `docs/superpowers/specs/2026-10-03-direct-messages-design.md`.
- **Consequences:** Hapus/keluar grup tidak memengaruhi DM; hapus akun menghapus DM-nya (CASCADE). `dm_subscribers` per proses — dengan beberapa worker uvicorn, SSE & penahanan notifikasi hanya akurat dalam worker yang sama (sama seperti chat grup). Deploy wajib restart service.
- **Addendum 2026-10-04 (Blokir):** tabel `dm_blocks (blocker_id, blocked_id)` per pasangan user (bukan per percakapan). Blokir dari salah satu pihak menolak kirim kedua arah (403 "Obrolan ini diblokir", tanpa notifikasi/SSE) dan menolak percakapan BARU; percakapan lama tetap dikembalikan & riwayat tetap terbaca. Buka blokir hanya menghapus blokir milik sendiri.

### ADR-006: Outbox dengan klasifikasi error, CAS/rev per record, `base_rev`/409 + salinan konflik, `client_id` idempoten
- **Date:** 2026-10-15
- **Agent:** Claude
- **Context:** Audit offline/sync (`docs/superpowers/specs/2026-10-15-offline-sync-audit.md`) menemukan kehilangan data diam-diam: token kedaluwarsa menghapus IndexedDB + outbox; push membuang op pada semua 4xx lalu pull menimpa record dirty; LWW berbasis `updated_at` (jam dinding, 3 format/zona) dikalahkan oleh proses non-pengguna (cron Eisenhower, `/share`, membuka note); record ditulis dari objek pra-request (edit in-flight hilang); POST tanpa idempotensi menggandakan task/habit/mindmap/pesan.
- **Decision:** (1) 401 = sesi berakhir, bukan ganti pengguna: data lokal dipertahankan, push setelah login ulang. (2) Respons push diklasifikasikan: jaringan/401/429/5xx → op tetap; 403 → `conflict:"access_lost"`; 404 → `conflict:"remote_deleted"`; 4xx lain → op dibuang + `record.sync_error` dan ditampilkan di conflict bar (Coba lagi / Buang). Record `dirty` tanpa op diantre ulang oleh pull, tidak ditimpa. (3) Setiap record punya `rev` (naik di tiap tulis lokal); semua tulis setelah jeda async lewat `TFdb.mutate` (satu transaksi baca-ubah-tulis); push menandai bersih hanya bila `rev` tidak berubah (`markPushed`). (4) PUT task/note/mindmap/drawing membawa `base_rev` opsional; server menjawab 409 `{"detail":{"code":"REV_MISMATCH","current":<row>}}` bila beda. Untuk note & mindmap konflik edit-vs-edit (409 atau pull) TIDAK memakai LWW: versi lokal disimpan sebagai entitas pribadi baru "(konflik) <judul>" (client_id baru), record asli mengadopsi server + notice `conflict_copy`; tidak dibuat bila isinya sama. Task tetap LWW (field kecil), drawing memakai three-way merge dengan `base_blob_ref`. (5) Semua create mengirim `client_id` (= cid); server mengembalikan baris yang ada bila `(user_id, client_id)` cocok (index unik parsial). (6) `updated_at` hanya berubah oleh edit pengguna: kuadran cron ditulis tanpa bump; klien mengadopsi field turunan (`quadrant`, `recurrence_end_date`, `recurrence_notif_level`, `completed_at`) terpisah. (7) Pull defensif: cek status HTTP, tiap langkah terisolasi (push selalu jalan), hapus lokal hanya setelah GET per item 404, tulis lewat CAS.
- **Consequences:** Pengguna bisa melihat lebih banyak item di conflict bar (sync_error, access_lost, salinan "(konflik)") — itu disengaja: tidak ada lagi kehilangan diam-diam. Klien lama (modul SW lama) tetap kompatibel: `base_rev`/`client_id` opsional di server. Rev/`client_id` mengubah bentuk record IndexedDB (tanpa migrasi skema; field baru opsional). SW `/` hanya di-cache bila versi index.html = versi SW (S11). Sisa: server masih `datetime.now()` naive (S9) — perubahan ke UTC disarankan sebagai ADR terpisah.

### ADR-007: Sesi login koheren antar-tab + perpanjangan token geser (sliding) dengan batas 30 hari
- **Date:** 2026-10-17
- **Agent:** Claude
- **Context:** Bapak: "sudah login, pindah tab, kadang perlu login lagi". Token disimpan di `localStorage.tf_token` (bersama semua tab) tetapi tiap tab memegang salinan `__token` yang dibaca sekali saat dimuat, tanpa listener `storage`. Akibatnya (direproduksi Playwright): login di satu tab tidak memulihkan tab lain yang sudah di form login (S1); 401 basi di tab lain menghapus token baru dari localStorage (S2); logout di satu tab tidak mengeluarkan tab lain padahal IndexedDB sudah dihapus (S3). Ditambah JWT 72 jam tanpa perpanjangan, dan sejak ADR-006 setiap 401 langsung memunculkan form login (tepat saat tab kembali aktif → `fetchAll` → `sync()`). Server mendahulukan cookie dan mengabaikan header walau token cookie tidak valid/beda akun.
- **Decision:** (1) `localStorage.tf_token` = sumber kebenaran; `__token` disinkronkan lewat event `storage` + baca ulang saat `visibilitychange`/`focus`/`pageshow` (`onSharedTokenChanged`), kecuali tulis localStorage gagal (`__tokenWriteFailed`). (2) Setiap 401 dilaporkan SEKALI dengan token yang dikirim request itu (`api.fetch`, `__syncTransport`, `__syncRawFetch`, `tryAuth`) ke `handleAuthExpired(failedToken)`: localStorage berisi token lain milik akun yang sama → adopsi + ulangi (tanpa form login); token akun lain → diserahkan ke App; selain itu sesi berakhir (hapus token hanya bila masih token yang gagal). Listener `tf:auth-expired` dan laporan 401 di `stepFailed` dihapus. (3) Aksi tab saat token bersama berubah (`sharedTokenAction`): logout manual → reload, sesi berakhir → form login, login akun sama → pulihkan sesi (`__restoreSession`), akun lain → `beginTabReload()` (tab tidak mengirim apa pun sampai reload). (4) Perpanjangan geser: klien memanggil `POST /api/auth/refresh` saat umur token ≥ 1/3 masa berlaku (24 jam dari 72), throttle antar-tab 10 menit, tidak menulis token bila logout dimulai (`beginLogoutGuard`/`tf_logout_at`) atau token berganti saat in-flight. Server: klaim `iat`, `auth_time` (saat login password, dibawa terus), `pwv` (sidik jari hash password); refresh ditolak bila `pwv` beda (password diganti) dan `{renewed:false}` bila `auth_time` > `SESSION_MAX_DAYS` (default 30). Cookie diperbarui hanya bila request membawa cookie. (5) `_resolve_user`: header Bearer → cookie → query; fallback ke kandidat berikutnya hanya bila `sub`-nya sama dengan `sub` kandidat pertama (tanpa verifikasi).
- **Consequences:** Pengguna aktif tidak lagi terlempar ke form login tiap 72 jam; yang tidak membuka app > 72 jam tetap login ulang, dan semua sesi wajib login password lagi paling lambat 30 hari. Semua tab mengikuti satu status sesi (multi-akun paralel dalam satu profil browser memang tidak didukung — IndexedDB dipakai bersama). Trade-off keamanan: token curian bisa diperpanjang sampai 30 hari (dulu 72 jam); logout dan ganti password belum mencabut token yang sudah terbit (ganti password hanya mencegah perpanjangan). Sisa jendela sempit: respons refresh yang dikirim tab lain tepat sebelum logout bisa menyetel ulang cookie httponly (≤ 72 jam). Tindak lanjut yang disarankan: kolom `token_epoch` per user (dinaikkan saat ganti/reset password, dicek di `_validate_token`), URL SSE Tauri dibangun ulang saat token berganti, bootstrap sesi dari cookie untuk magic link Telegram.

### ADR-008: Peta tertaut (Petakan) — catatan satu-satunya sumber data
- **Date:** 2026-10-18
- **Agent:** Claude
- **Status:** Desain disetujui Bapak (brainstorming per bagian); implementasi belum dimulai.
- **Context:** Bapak ingin mindmap dibuat otomatis dari catatan: hierarki node = daftar isi (heading) catatan, dua arah (edit di peta mengubah catatan dan sebaliknya), dengan logika aturan tanpa LLM karena sebagian user tidak ingin datanya dikonsumsi LLM. Dua alternatif ditolak: (a) menyimpan salinan pohon di mindmap + mesin sinkron dua arah — data ganda yang bisa berselisih dan risiko tertinggi merusak isi catatan; (b) mode tampilan di dalam catatan saja — tidak muncul di halaman Mindmap/tab dan menyulitkan pengembangan lanjutan.
- **Decision:** (1) Peta tertaut = baris `mindmaps` dengan `source_note_id` (index unik parsial; sengaja tanpa FK cascade karena Sampah catatan memakai DELETE + restore dengan id yang sama, ADR-004). `data_json` hanya pengaturan tampilan (arah, Justify, lipatan, ringkasan); server menolak `nodeData` untuk peta tertaut. (2) Pohon dibangun ulang dari markdown catatan oleh `static/offline/notemap.js` (fungsi murni, mengikuti aturan heading daftar isi mode edit). Edit peta disusun ulang jadi markdown — bagian lama disalin byte per byte, identitas node lewat `nm.sid`, level heading mengikuti aturan saudara/induk, batas H6 — lalu ditulis lewat `noterepo.applyMapEdit` di dalam `TFdb.mutate` atas isi catatan terbaru; bila isi sudah berubah, edit dibatalkan dan peta dimuat ulang (tidak digabung). (3) Pemilik dan `list_id` peta selalu sama dengan catatan; server menyamakannya setiap catatan dibuat/disimpan/di-share/dipulihkan, dan menghapus peta saat catatan dihapus permanen. (4) Pengaturan tampilan memakai "yang terakhir menang" tanpa salinan konflik; isi peta ikut sinkron dan konflik catatan (ADR-006). (5) `GET` daftar mindmap menyaring peta tertaut kecuali klien mengirim `?linked=1`, supaya APK/cache lama tidak membukanya sebagai peta kosong.
- **Consequences:** Dua arah konsisten karena hanya ada satu sumber data; offline, sinkron, dan konflik tidak butuh mekanisme baru. Peta tertaut tidak bisa memuat isi khusus peta (panah antar node, kurung Summary, link node dimatikan) dan tidak bisa dibuka tanpa akses ke catatannya. Edit peta yang bentrok dengan perubahan catatan harus diulang user. Spec: `docs/superpowers/specs/2026-10-18-petakan-note-mindmap-design.md`.

### ADR-009: Akses publik drawing & lampiran mengikuti "note publish tepercaya"; ekspor DOCX mengikuti akses pengekspor
- **Date:** 2026-10-18
- **Agent:** Claude
- **Context:** Halaman publik (`/pub/...`, tanpa login, satu origin dengan app) dan ekspor DOCX (pendaftaran terbuka) me-resolve drawing/lampiran tanpa filter pemilik: `/pub/drawings/{id}` melayani drawing siapa pun, render publik mencocokkan id/judul lintas user + fallback `id = note_id`, seksi kanvas legacy menanam drawing `id = note_id`, lampiran/backlink/wikilink mengabaikan password note, resolver ekspor lintas user. Isi note bersama bisa diedit anggota, dan note bersama bisa menjadi "pribadi" lewat unshare atau penghapusan workspace (`ON DELETE SET NULL`) tanpa campur tangan pemilik.
- **Decision:** (1) Note publish **tepercaya** = `list_id` kosong + `scratchpad_notes.user_id = published_notes.user_id` + (`last_edited_by` kosong atau = pemilik). (2) Drawing tampil publik hanya bila dirujuk `::draw[id|client_id]` di note tepercaya dan dimiliki penerbit; resolusi hanya lewat id/`client_id` (tanpa judul, tanpa `id = note_id`); seksi kanvas legacy dihapus. (3) Note berpassword: drawing dan lampiran butuh cookie `pub_unlock_{slug}`; "Related" tidak memuat note berpassword; wikilink ke note berpassword hanya dari note tepercaya milik pemiliknya. (4) Metadata user lain di halaman publik di-escape. (5) Ekspor DOCX: drawing hanya milik pengekspor (tanpa tebak judul untuk token id/UUID); lampiran hanya dari note yang bisa diakses pengekspor atau dipublish tanpa password. (6) Semua penolakan = 404 yang sama dengan "tidak ditemukan"; id di luar INTEGER 64-bit → 404.
- **Consequences:** Drawing di note publish bersama dan di note yang terakhir disunting orang lain tidak tampil publik (PR 2 menambah drawing workspace `list_id = W` untuk note bersama). Sisa risiko yang diterima: setelah pemilik menyimpan note lagi, sisipan lama ikut dipercaya (pemilik melihatnya di app). Belum ditangani: XSS isi note (PR 1b), SSRF ekspor, lampiran note bersama di app hanya untuk pengunggah.

### ADR-010: Project sebagai entitas ber-scope (pribadi / satu workspace); teks `tasks.project` tetap disimpan
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Project dulu hanya teks bebas di `tasks.project`; dropdown = `DISTINCT` dari task aktif milik user, jadi project hilang saat semua task selesai, tidak bisa dikelola, dan anggota workspace tidak berbagi daftar project. Bapak memilih project sebagai entitas dengan hak kelola opsi C (spec `docs/superpowers/specs/2026-10-18-workspace-drawing-project-design.md` §5).
- **Decision:** (1) Tabel `projects` dengan tepat satu pemilik (`user_id` XOR `list_id`), nama unik NOCASE per scope, `archived`, `created_by`; `tasks.project_id` FK `ON DELETE SET NULL`. (2) Teks `tasks.project` tetap diisi nama kanonis (bot, NLP, review, filter, klien lama). (3) Satu resolver `resolve_task_project` untuk semua jalur tulis; scope = workspace bila `list_id` menunjuk list yang ada, selain itu pribadi pemilik task; workspace mensyaratkan aktor anggota/owner; resolusi hanya saat project benar-benar berubah. (4) Backfill idempoten di setiap `migrate_db()`, tahan data rusak (SAVEPOINT per grup), memperbaiki link basi, tidak mem-bump `updated_at`. (5) Hak kelola opsi C: pakai/buat = semua anggota; rename/arsip/hapus = pembuat atau owner workspace; 404 bila tak terlihat, 403 bila terlihat tapi tak boleh kelola. (6) `GET /api/projects` tanpa parameter tetap `string[]` pribadi untuk klien lama.
- **Consequences:** Project tidak lagi hilang saat task selesai; dropdown per scope menunggu PR 5. Batasan v1: PUT task LWW tanpa `base_rev` → perangkat offline basi bisa membuat ulang project bernama lama setelah rename/hapus (PR 5 mengirim `project_id` + `base_rev`). Bot `/projects` hanya project pribadi dan kini juga menampilkan project tanpa task aktif.

### ADR-011: Daftar project di klien = cache server per scope + `project_ref_name` pada task
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** SPA local-first melayani `GET /api/projects` dari router lokal (turunan teks task), sehingga tabel `projects` (ADR-010) tidak terlihat dan project workspace tidak bisa dibagi. Perangkat offline yang basi bisa membuat ulang project bernama lama setelah rename/hapus.
- **Decision:** (1) Modul `static/offline/projectcache.js` menyimpan `GET /api/projects?format=full&scope=all&include_archived=1` di `_meta` "projects:v1", di-refresh tiap sync pull; route lokal `GET /api/projects` sadar scope (`?list_id=`, `format=full`), tanpa query tetap `string[]` pribadi. (2) Task menyimpan `project_ref_name`; push mengirim `project_id` selama teks = nama itu (server: id sama → tetap, id terhapus → diabaikan). (3) Kelola project hanya online lewat `api.fetch(..., {network:true})` yang menambah `X-TF-Sync: 1` agar melewati cache SW. (4) Form task memilih scope di baris atribut cepat; tampilan mengelompokkan per (scope, nama NOCASE). (5) Event `tf:projects-changed` setelah pull/kelola.
- **Consequences:** Anggota workspace berbagi daftar project yang sama, juga offline (dari cache + task lokal). `base_rev` task tetap tidak dipakai. Sisa yang diterima: pindah project offline ke project yang dihapus sebelum push → task tetap di project lama.

### ADR-012: Drawing berscope workspace (`drawing_scope.py`)
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Spec §4: drawing harus bisa dimiliki satu workspace seperti mindmap, supaya anggota yang membuka note W melihat semua drawing di dalamnya, tanpa share otomatis yang tidak disengaja.
- **Decision:** (1) Modul `drawing_scope.py` (tanpa impor webapp): skema `drawings.list_id`/`last_edited_by` (FK SET NULL), backfill **sekali jalan** (flag `app_meta['drawing_list_backfill_v1']`), access clause, lookup token id → `client_id` milik sendiri dulu, sinkron note → drawing, aturan publik. (2) `GET /api/drawings` tanpa parameter tetap milik sendiri; `?shared=1` untuk klien baru (PR 3). (3) Share/unshare/pindah hanya pemilik; ditolak 409 `DRAWING_IN_USE` bila masih dipakai note W (judul hanya yang terlihat pemilik + `hidden_count`). (4) **Server memindah drawing hanya saat penulisan menetapkan/mengubah `list_id` note** (share, note baru di W); autosave/PUT biasa dan restore tidak pernah memindah. Sisip drawing pribadi ke note W yang ada → klien memanggil share eksplisit (PR 3). (5) Regex direktif tidak peka huruf besar/kecil, sama dengan klien. (6) Halaman publik: note tepercaya → drawing yang bisa diakses penerbit; note bersama W → hanya `list_id = W`; query `/pub/drawings` dibatasi penerbit di SQL. (7) Hapus workspace mem-bump `updated_at` drawing yang kembali pribadi (`repository.delete_shared_list`).
- **Consequences:** Sampai PR 3, drawing yang disisipkan ke note W yang sudah ada tetap pribadi (anggota melihat placeholder). Sisa risiko yang sama kelasnya dengan §3: note bersama yang di-unshare/workspace-nya dihapus setelah pemilik menyimpannya menjadi tepercaya, sehingga sisipan anggota (drawing pribadi pemilik) bisa tampil di halaman publik. Deploy: restart `taskflow-web` dan `taskflow`.

### ADR-013: Drawing workspace di aplikasi (PR 3) — share online, salin lokal, scope dari server
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Lanjutan ADR-012: klien harus menampilkan, membagikan, dan menyalin drawing berscope workspace tanpa kehilangan edit offline.
- **Decision:** (1) Record drawing lokal menyimpan `list_id`/`user_id`/`last_edited_by`/`last_editor_*`; pull memakai `/api/drawings?shared=1` dan mengadopsi metadata scope setiap kali berbeda (terpisah dari konten). (2) Drawing orang lain yang hilang dari daftar: bersih → dihapus lokal, dirty → konflik `access_lost` (keep_as_new menjadikan salinan milik user saat ini). (3) Share/unshare hanya online lewat `TF.drawingshare.shareDrawing`; **hanya `list_id` yang diadopsi, `base_rev` tidak dimajukan** (PUT drawing tidak membawa `base_rev`, jadi memajukannya menyembunyikan edit anggota lain dari pull). (4) Salin memakai data lokal bila ada (jalan offline), selain itu `POST /copy`. (5) Share note ke W selalu flush + push lalu cek sinkron sebelum `PATCH share`; dialog menyebut drawing yang ikut/disalin, `moved_drawings` di luar rencana di-toast. (6) Hapus/pin drawing orang lain ditolak lokal (403) sebelum masuk outbox. (7) Daftar drawing di halaman workspace (§4.7) diganti filter scope di halaman Draw.
- **Consequences:** SW v421. Setelah update, perangkat mengunduh ulang konten drawing yang di-share satu kali. Sisa diterima: pull yang daftar-nya lebih tua dari share lokal bisa sesaat mengembalikan scope lama (sembuh di pull berikutnya).

### ADR-014: Sampah mindmap = snapshot + cermin offline; pin mindmap per user; `mindmaps.search_text`
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Temuan review mindmap #5–#8 (spec `docs/superpowers/specs/2026-10-19-mindmap-findings-3-8-design.md`): hapus mindmap = hard delete, pin hanya pemilik (anggota gagal diam-diam), `/api/search` mencocokkan `data_json LIKE` (kunci JSON seperti "children" ikut cocok), mindmap tidak ikut ekspor; kartu link node hanya snapshot (#3).

### ADR-015: Kolaborasi langsung mindmap — merge tiga arah per node di klien, SSE hanya sinyal, stream hanya untuk tab aktif
- **Date:** 2026-10-19
- **Agent:** Claude
- **Context:** Temuan review mindmap #4 (spec `docs/superpowers/specs/2026-10-19-mindmap-findings-3-8-design.md` §#4): peta bersama baru berubah lewat sinkron 30 detik, dan edit bersamaan di node mana pun membuat salinan konflik seluruh peta (ADR-006).
- **Decision:** (1) **Merge per node di klien**: `static/offline/mindmapmerge.js` (`TF.mindmapmerge.merge3(B, L, S)`, modul murni) dipakai saat push 409 `REV_MISMATCH`, saat pull menemukan record dirty yang berubah di server, dan di router lokal `PUT /api/mindmaps/:id` (body `base_data_json` dari tab). Basis = `base_data_json`/`base_title` pada record (isi server pada `base_rev`). Node berbeda → digabung tanpa salinan; field yang sama di node yang sama → versi server di peta bersama + salinan pribadi "(konflik) <judul>" versi lokal utuh + notice `merge_conflict`; posisi/urutan/lipatan/panah/ringkasan/pengaturan/judul → server menang tanpa salinan; edit menang atas hapus. Server tetap otoritatif (`base_rev` + 409 tidak berubah) dan tidak tahu basis. Record tanpa basis/JSON rusak/fallback → perilaku lama (salinan seluruh peta). Salinan konflik dari push 409 / pull memicu event window `mindmapConflictCopy` → toast (jalur simpan tab memberi toast dari respons router); merge bersih tidak memberi toast. (2) **SSE hanya sinyal**: `GET /api/mindmaps/{mid}/stream` mengirim `mindmap_changed`/`mindmap_deleted`/`mindmap_access_lost` tanpa isi; klien mengambil isi lewat `pullMindmapOne` di dalam `runSyncExclusive` (bus dalam proses, cukup karena uvicorn satu proses). SW: stream network-only. Sinkron 30 s tetap jadi cadangan. (3) **Stream hanya untuk tab mindmap yang aktif** (ruling controller): HTTP/2 di produksi tidak bisa dipastikan dari repo (konfigurasi nginx tanpa `http2`) dan HTTP/1.1 hanya memberi 6 koneksi per origin, jadi satu `EventSource` per tab terbuka bisa menghabiskan pool. Mengaktifkan tab membuka stream dan `onopen` menarik satu peta untuk mengejar perubahan yang terlewat; tab latar belakang tidak langsung, tetapi mengejar saat diaktifkan. (4) **Undo dikosongkan setelah pembaruan jarak jauh** (`TF.mindmapops.resetUndo` → `clearHistory()` mind-elixir, juga setelah `refresh` dari Outline) — kalau tidak, Ctrl+Z memulihkan pohon sebelum pembaruan dan simpan berikutnya menghapus perubahan anggota lain. (5) **Salinan konflik dipakai ulang per sesi tab**: salinan dari router lokal diberi `conflict_session` = `session_id` instans tab; konflik berikutnya dari tab yang sama memperbarui salinan itu, sedangkan salinan dari pull/409 (tanpa sesi) dan dari tab lain selalu salinan baru — tidak ada salinan yang menimpa isi milik sesi lain. (6) **Peta tertaut (Petakan, `source_note_id`) tidak pernah di-merge dan tidak berlangganan SSE** (stream 404 untuk peta tertaut); ADR-008 tetap berlaku.
- **Consequences:** Deploy wajib `sudo systemctl restart taskflow-web` (endpoint stream + broadcast di `webapp.py`). SW `taskflow-v423-mindmap-live`, iframe `?v=145`. Record mindmap kira-kira 2× ukuran (`base_data_json`). Tab latar belakang tidak live sampai diaktifkan. Edit Outline yang sedang diketik bisa batal bila nodenya hilang oleh pembaruan jarak jauh (diterima). Setelah 8 kegagalan sambung berturut-turut stream berhenti sampai online/aktivasi tab; sinkron 30 s menutup celah. Riwayat undo kanvas hilang setiap kali pembaruan jarak jauh diterapkan. Record yang isinya sama dengan basis tab (gema simpan sendiri, catch-up tanpa perubahan) tidak memuat ulang kanvas. Riwayat undo Outline juga dikosongkan saat pembaruan jarak jauh diterapkan (`historyEpoch`). Pelanggan stream yang dilepas (antrean penuh) ditutup sehingga klien menyambung ulang.

### ADR-019: Papan Kanban tahap: model murni + tahap pending offline di `_meta`
- **Date:** 2026-10-20
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-19-kanban-context-stages-design.md` (§7–§8), di atas backend ADR-016: papan Kanban Group by Context harus menampilkan tahap (termasuk yang kosong) per scope, kolom "Belum ada tahap" dan "Selesai", drag mouse + sentuh, kelola tahap, dan membuat tahap saat offline. Klien sebelumnya hanya mengenal teks `task.context`, drop mem-`parseInt` id (task cid tidak bisa diseret), dan tidak ada jalur "buka lagi" task done.
- **Decision:** (1) **Model papan murni** `static/offline/kanbanboard.js` (tanpa DOM/IndexedDB): bentuk kolom `{key, kind: none|stage|orphan|done|priority|project, …}`, pencocokan task → tahap **id dulu** (`context_id`), lalu nama NOCASE; tahap diarsip / nama tanpa tahap jadi kolom "orphan" (" (diarsip)" / " (belum tersinkron)", bukan target drop); keputusan drop (`dropAction`) dan urutan kartu (P1→P4, deadline, judul NOCASE, id; "Selesai" = `completed_at` terbaru) diuji sebagai fungsi murni. Id task/tahap selalu string apa adanya (`String(a) === String(b)`), tanpa `parseInt`. (2) **Cache tahap** `contextcache.js` (pola `projectcache`, ADR-011): `_meta` `contexts:v1` disegarkan setelah pull; **tahap yang dibuat offline disimpan di `_meta` kunci `contexts:pending:v1`** (R1) — tanpa store IndexedDB baru, `DB_VERSION` tetap 5 — dengan op outbox `{entity_type:"context", op:"create"}`. Op task (create **dan** update) yang `context_id`-nya masih cid tahap pending **ditahan** sampai op tahap terkirim; sukses → cid dipetakan ke id server di semua task lokal (CAS, dirty + rev), gagal permanen → `context_id` dibuang dan task terkirim dengan nama saja. `context_id` cid tidak pernah dikirim ke server. (3) **Rute**: `GET`/`POST /api/contexts` lokal; `PATCH`/`DELETE /api/contexts/{id}` dan `PUT /api/contexts/order` sengaja tidak lokal (kelola tahap = online saja, modal memakai `GET … {network:true}`). (4) **K1** — task berulang ke "Selesai" (drop atau checkbox) menandai *occurrence hari ini* (Asia/Jakarta) lewat `POST /api/tasks/{id}/occurrences/{hari}/mark`, kartu tetap di tahapnya; offline → toast "Tidak bisa dilakukan saat offline". **K2** — keluar dari "Selesai" membuka lagi task dengan `gtd_status:"next"` + context tujuan. (6) **Drag = Pointer Events** (mouse mulai setelah 6 px; sentuh setelah tekan-tahan ≥ 250 ms tanpa bergeser, listener `touchmove` non-pasif dipasang sejak mount), kolom target lewat `data-kanban-col`; menu "Pindah ke…" per kartu sebagai alternatif tanpa drag. Scope papan halaman non-workspace disimpan per halaman di `localStorage` `tf_kanban_scope:<page>`.
- **Consequences:** Kegagalan permanen create tahap tidak tampil di conflict bar (tahap pending bukan entitas store); pengguna hanya melihat toast saat drop/buat dan tahap hilang setelah sync. Klien lama (SW < v426) yang menerima op `context` akan membuangnya (fallthrough `processOp`), sehingga rilis butuh bump SW **`taskflow-v426-kanban-stages`**. "Selesai" hanya memuat 7 hari terakhir; halaman "done" pada mode Kanban tidak lagi menampilkan task done yang lebih lama. Status sebelum done tidak disimpan, jadi K2 selalu memakai `next`. Rename/hapus tahap menarik ulang task (teks context ikut berubah di server, ADR-016). Deploy: hanya file statis + `webapp.py` (`sw_cache`) → restart `taskflow-web` agar `/api/version` melaporkan v426. Diverifikasi E2E Playwright `temporary_files/e2e_kanban_stages.py` (mouse, sentuh CDP, offline, dua perangkat).
- **Biaya R3:** urutan tahap di modal "Kelola tahap" lewat tombol ↑/↓ (satu langkah + satu `PUT /api/contexts/order` per klik) kurang mulus dibanding drag urutan yang disebut spec §7.5; drag tetap ada di papan (kartu antar kolom), dan urutan kolom di papan juga bisa lewat menu ⋯ "Geser ke kiri/kanan".

### ADR-022: pwv diperiksa di setiap request + `users.password_set` untuk akun Telegram
- **Date:** 2026-10-21
- **Agent:** Claude
- **Context:** Klaim JWT `pwv` (sidik jari `password_hash`) sebelumnya hanya dicek di `POST /api/auth/refresh`, sehingga ganti/reset password tidak mengeluarkan perangkat lain sampai token kedaluwarsa (≤ `JWT_EXPIRE_HOURS`). Frontend sudah memanggil `PATCH /api/auth/profile/password` dan `/username` (404). Akun yang dibuat otomatis dari Telegram (`tg_<telegram_id>`) memiliki password acak yang tidak diketahui pemiliknya, sehingga tidak bisa ganti password (butuh password lama) atau login web.
- **Decision:** (1) `_validate_token` memuat `username, password_hash` user (satu lookup PK untuk setiap token). Token non-ext dengan `pwv`: beda/user hilang → 401 "Password sudah diganti — masuk lagi". Token tanpa `pwv` tetap diterima (kompatibel token lama). Untuk semua token (termasuk ext) klaim `username` ditimpa nilai DB bila baris ada, sehingga log aktivitas/notifikasi/mention/pembuatan token ext tidak memakai nama basi. Fallback kandidat di `_resolve_user` tidak berubah. Stream SSE (`chat_stream`, `dm_stream`, `mindmap_stream`) memanggil `_session_still_valid(user)` di setiap keepalive (±20 dtk) dan menutup stream bila password sudah diganti. (2) Kolom `users.password_set INTEGER NOT NULL DEFAULT 1` lewat migrasi idempoten di `_init_db`; hanya saat kolom baru ditambahkan, akun `username = 'tg_' || telegram_id`, atau `telegram_id IS NULL AND username GLOB 'tg_[0-9]*'` (Telegram sudah dilepas), ditandai 0. Register menolak username berawalan `tg_` (case-insensitive); aturan charset baru tidak diterapkan ke register. `auto_register_telegram_user` menyisipkan 0. (3) `PATCH /api/auth/profile/password` (butuh password lama), `PATCH /api/auth/profile/username` (butuh password; `^[A-Za-z0-9_]{3,50}$`, tidak boleh diawali `tg_`, display_name tidak diubah), `POST /api/auth/complete-account` (hanya `password_set = 0`, tanpa password lama; email wajib, username opsional, atomik). Ketiganya menerbitkan token baru (auth_time pemanggil dipertahankan — bila tidak ada, diperkirakan dari `exp` seperti refresh — pwv baru) dan memperbarui cookie hanya bila request membawa cookie `token`; token ekstensi ditolak (403). (4) Ganti password, lengkapi akun, dan `/api/auth/reset` menghapus semua `ext_tokens` user dan menyetel `password_set = 1`. (5) `GET /api/auth/me` mengembalikan `password_set`.
- **Consequences:** Satu query SQLite tambahan per request terautentikasi (lookup PK, murah) dan satu per keepalive SSE. Ganti/reset password langsung mengeluarkan perangkat lain, stream SSE terbuka (dalam ±20 dtk), dan Browser Clipper (harus dihubungkan ulang). Mengganti username tidak membatalkan token lain (pwv tetap); klaim `username` di token lama basi tetapi server selalu memakai nilai DB. Akun tg_ yang mengganti username tidak lagi dianggap "akun otomatis" oleh `/link` di bot (deteksi `startswith("tg_")`). Deploy: restart `taskflow-web` dan `taskflow` (migrasi kolom).

### ADR-024: Komentar note = tabel terpisah `note_comments` (soft delete, `list_id` saat dibuat menentukan visibilitas, tanpa FK ke note)
- **Date:** 2026-10-21
- **Agent:** Claude
- **Context:** Anggota workspace perlu meninjau note bersama lewat komentar tanpa mengubah isi note, dan Alurik local-first (komentar harus bisa disinkronkan offline lewat delta pull berkursor). Note bisa ke Sampah, di-restore, di-unshare, dipindah ke workspace lain, atau workspace-nya dihapus; komentar harus mengikuti siklus itu tanpa bocor ke orang yang tak berhak. Menyimpan komentar di dalam konten note akan mengubah `updated_at` note dan bentrok dengan sinkron note.
- **Decision:** (1) Tabel `note_comments` (id, `note_id` tanpa FK, `list_id` workspace saat komentar dibuat, `user_id`, `parent_id` satu tingkat, `body` 1-4000, `quote` <= 500 hanya di thread, `resolved_at/by`, `edited_at`, `deleted_at`, `client_id`, `created_at`, `updated_at` sebagai kursor) + `note_comment_reads` (`last_read_at` per user per note) + kolom `notifications.note_id`; migrasi idempoten. (2) Visibilitas satu helper `note_comments.visible_clause(uid)` (plus `note_comments.visible_note`): note ada, `n.list_id IS NOT NULL`, `n.list_id = c.list_id`, dan lolos `_note_access_clause`. Karena itu note ke Sampah / di-unshare / dipindah workspace otomatis menyembunyikan komentar tanpa menyentuh barisnya; restore atau share ulang ke workspace sama memunculkannya lagi. (3) Hapus = soft delete (tombstone, `body` dikosongkan; thread menghapus balasannya) agar delta pull `GET /api/note-comments?since=<updated_at>|<id>` bisa menyampaikan penghapusan. Tombstone > 30 hari dibersihkan di `migrate_db()` saat start/deploy; kursor lebih tua dari 30 hari dijawab `{"reset": true}`. (4) Hak: edit hanya penulis; selesaikan/buka lagi thread oleh penulis thread + pemilik note; hapus oleh penulis + pemilik note. (5) Idempotensi POST lewat unique index `(user_id, client_id)`. (6) Badge turunan `comment_open_count` / `comment_unread` di daftar/detail note lewat subquery, tanpa mengubah `updated_at` note. (7) Notifikasi in-app + Telegram lewat `_notify_users_bg`; SSE `GET /api/scratchpad/{id}/comments/stream` hanya mengirim sinyal `comments_changed` dengan cek akses ulang per pelanggan.
- **Consequences:** Komentar tidak ikut Sampah (tidak ada di snapshot), ekspor DOCX/MD, `/pub`, pencarian, dan backlink. Purge note / kosongkan Sampah / hapus workspace menghapus baris komentar permanen. Tombstone bisa bertahan lebih dari 30 hari sampai restart/deploy berikutnya; klien tetap benar karena kursor > 30 hari dijawab `reset` dan klien menarik ulang. Komentar pada note yang dipindah ke workspace lain tetap tersembunyi (bukan dihapus). Tanpa FK ke note berarti pembersihan harus eksplisit di setiap jalur hapus note. PR 2 (offline) dan PR 3 (UI) memakai kontrak ini.

### ADR-027: Cakupan dan bucket waktu halaman Fokus dihitung di klien dengan tanggal lokal

### ADR-029: Precache SW — shell atomik dan revalidasi
- **Date:** 2026-10-23
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-22-sw-precache-shell-design.md`. Setelah HP restart, Alurik tampil tanpa styling. `/static/app.css?v=362` tidak di-precache dan `milkdown.bundle.js` tercatat tanpa `?v=289`, padahal catch-all `fetch` mencocokkan URL persis dan `activate` menghapus cache versi lain, jadi tiap rilis keduanya wajib diambil ulang dari jaringan (gagal → 503, stylesheet dibuang). (4) Tes `tests/offline/sw_precache_shell.test.js` menjaga: aset lokal `index.html` ada di `STATIC` dengan URL persis, entri `STATIC` adalah file yang ter-track git, tanpa entri ganda; ikut CI lewat `tests/test_sw_precache_node.py`. `activate`, cabang `fetch`, server, dan skema tidak berubah.
- **Consequences:** Update bisa tertunda sampai jaringan cukup baik untuk memvalidasi seluruh shell. Setiap file baru yang dimuat `index.html` wajib ditambahkan ke `STATIC` dengan URL persis (dijaga tes). tldraw/ikon/KaTeX tetap bisa hilang sampai dipakai online. URL ganda atau URL yang 404 di `STATIC` memblokir semua update (dijaga tes + CI; deploy belum menunggu tes, lihat tindak lanjut H). Perangkat dengan penyimpanan hampir penuh (`QuotaExceededError`) bertahan di versi lama sampai ruang cukup. Setiap percobaan install ulang tetap mengunduh `/` penuh (`no-store`) sampai tindak lanjut F. Perlindungan sudah berlaku untuk rilis v464 sendiri (install/activate yang berjalan milik SW baru). Deploy: file statis + `webapp.py` (`sw_cache` v464) → restart `taskflow-web`; tanpa migrasi.

### ADR-031: Satu isi detail task untuk modal dan panel; panel Live Edit menyimpan otomatis per field yang berubah
- **Date:** 2026-10-26
- **Agent:** Claude
- **Context:** Spec `docs/superpowers/specs/2026-10-26-live-edit-design.md`. Bapak ingin mengedit satu task cukup lama lalu pindah ke task berikutnya tanpa menutup modal setiap kali.
